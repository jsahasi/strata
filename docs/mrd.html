Market Requirements Document

The market, not the user. The PRD argues that one analyst has a real problem; this document argues that the problem sits inside a market big enough, urgent enough, and defensible enough to build a company on — and says where that argument is not yet proven.

The five requirement areas, and where each one stands

Five requirement areas define what this product must deliver: retrieval with citations, change detection at scale, document intelligence, human-in-the-loop review, and auditability. They are stated in the vocabulary the category is specified in, so that each requirement can be traced from the name it is asked for by to the code that serves it — or to the gap where that code is not yet written.

How the five relate to the eleven below. The eleven are build areas — the parts this repository is made of, named the way the code names them. The five are requirement areas: what the work has to deliver. They cross rather than nest. Citation verification is one build area and half of one requirement; document intelligence is one requirement and no build area at all. Both tables read the same code, and neither is a summary of the other.

Four of the five are PARTIAL and one is NOT BUILT. None is fully served, and document intelligence has one regex behind it. Every gap named below was read out of the code, not estimated from the plan.

1. Retrieval with citations — PARTIAL

The citation half is the strongest thing in this repository. Every claim binds to (version_id, char_start, char_end, quoted_text) plus the occurrence index where the quote is not unique, and app/state/claims.py re-verifies it against the stored bytes on every render rather than reading a stored verdict. On that path the verifier refuses an empty span, an inverted span, offsets past the end, a quote that does not match, a quote that appears twice without naming which one, and a version this company may not read. It also pairs each claim with the text of the version the claim names, from a map built through the tenant chokepoint, so a citation cannot pass on words that happen to sit at those offsets in a different version. A claim that fails has no statement field to leak, so it cannot half-assert itself. That is the product, and it is visible at /changes/CHG-v1-v2-003.

The check that would catch a drifted source is not on that path. The verifier re-reads the bytes under the citation, so an edit landing on a cited span withholds the claim on the next render. An edit elsewhere in the same version does not. verify_citation_for_version() hashes a version's stored text and refuses when the digest disagrees with the one ingestion recorded — and nothing under app/ calls it; tests/test_verification.py does. The render path is verified_claims() in app/state/claims.py, which calls the plain verify_citation() and compares no hash. Both modules say so in their own docstrings. Measured: seed a claim, edit twenty characters of that version well away from the cited span, leave the stored SHA untouched, and verified_claims() still returns the claim as verified — which is what the change view renders — while the digest of the stored text disagrees with the stored one. Closing it needs a single-row scoped read in app/state/queries.py that does not exist yet, and a decision about what the change view shows for a drifted source. The control is proved in the module and absent from the product — the same defect named under Human-in-the-loop review below about the approval gate.

Two things this requirement asks for are absent. There is no page. A citation addresses characters into a frozen text; an analyst cites “Exhibit JS-3 at 12”, and this product cannot say that, because the corpus is plain text with no pagination and DocumentVersion carries no page map. The fix is a page index built at ingestion from the PDF layer that does not exist yet — it is additive, not a redesign, and it is not done. Retrieval is an index. app/state/search.py is FTS5 with bm25 ranking over the passage store, scoped through queries.py like every other tenant read: 1.3ms against 366ms on 8,707 passages. It replaced a substring match on 2026-08-04: search_claims() in app/chat/tools.py used to walk every change on the company's record and keep the claims whose own statement contained the words, so a claim was reachable only through the sentence it had already written, never through the filing it cites. It is deliberately not a search feature and there is no search box — ADR-02 rejected search as the wedge and ADR-71 explains at length why retrieval inside the citation path is a different thing. A ranked hit is a candidate that still has to pass verify_citation, and a passage carrying the cited span of a withheld claim is not offered at all. The refusal is the part it gets right: a withheld claim cannot be searched, because its statement is never handed back, so every withheld claim in scope is reported by count and reason instead of being silently absent from the results. The module table in A4 of the TDD describes it, and requirements.txt explains why no vector store is pinned. So the checking half is built hard and the finding half is real but narrow: lexical retrieval exists and is indexed; it reaches the record only through the assistant, so a machine with no ANTHROPIC_API_KEY gets none of it; and the semantic half — the one ADR-08 reserved for matching a docket change to an obligation written in the company's own words, which is the product's core join — is still an intention with no vector store behind it.

2. Change detection at scale — PARTIAL

The architecture here is deliberate and it is the right way round (ADR-004). The diff is a pure function — two passage sequences in, typed changes out, no model, no clock, no randomness — so the model is never asked “did anything change”, only “does this change matter”. On top of it sits the load-bearing design decision in this area: when two passages read almost identically but sit under different section numbers, alignment confidence is capped at 0.5, because a renumbered section is exactly the case where text similarity runs high and structural identity has changed. A restructure escalates instead of presenting itself as a settled match.

There are two corpora, both labelled, and “at scale” is the part that does not hold. The synthetic one is three text files of one invented proceeding, and it stays because its traps are deliberate (ADR-40): one sentence repeated three times per version, and a restructure that scores 0.944 on raw similarity. The eval numbers are measured against those and a real filing will not reproduce them on demand. The second corpus is real: data/real/ holds 102 public filings from eight state commissions, each beside a provenance file naming the docket, the filer, the date and the URL it came from. scripts/ingest_real.py loads one pair of them into the workspace — Kentucky PSC 2025-00113, Lane Kollen's direct testimony, filed 2025-09-09 and corrected 2025-09-30, 1,024,409 characters against 1,024,536. The pipeline finds 144 changes in it. That is the market argument stated as arithmetic: a 127-character difference across a million characters, on a document a person really filed, with a link back to the commission's own copy. The filer also published a marked-up version saying what they changed, which is the first ground truth on this project nobody on this side wrote.

What still does not hold is the fetching. There is no FERC connector and no state PUC connector. The integrations screen registers the eight commissions the real corpus came from and prints FETCHES_NOTHING at the top of the page, in words a buyer can quote, because FETCHABLE_SOURCE_KINDS is empty and every row therefore answers that no fetcher exists for its kind. ScheduledRun stores a cadence, a next run and a last result, and no code reads next_run_at to fire anything. The 102 filings arrived because agents were sent to the commission portals by hand; nothing in the product can repeat that.

“Semantically meaningful rather than text diffs” is the weak point. What ships on the diff path is difflib.SequenceMatcher over normalized text, plus a section-label check. The confidence cap detects when that text diff is unreliable, which is genuinely useful and usually skipped — but detecting an unreliable diff is not understanding meaning. Semantic materiality is the job the interpretation stage would do. app/interpretation/propose.py now asks Claude exactly that question, binds every proposal to a citation the verifier re-reads, and drops the ones that fail — and nothing under app/ or scripts/ calls it. app/pipeline.py still calls no model and still leaves Change.materiality NULL rather than defaulting it to something that reads like a judgement.

3. Document intelligence — NOT BUILT

The whole of the structural understanding is one regular expression in app/ingestion/ingest.py that recognises “SECTION 4. STUDY PROCESS” and “4.4 Study Timelines” and records the number — 4, or 5.4.1 — on each passage. That number is what the diff compares to cap confidence, so it earns its place. It is not document intelligence, and this is the weakest of the five.

There is no exhibit model, no testimony structure, no cross-reference resolution and no precedent chain. The one grep hit for precedent is a knowledge-item kind, and the seeded row under it is a human-authored note about draft-versus-final handling — a person's lesson, deliberately written by a person, not a chain a parser found. The synthetic corpus already contains the feature. data/manifest.json documents a restructure where Section 6 becomes 5.4, its subsections renumber, and the internal cross-references follow — including a ripple in Section 4.5 that points at the moved text. The trap is built, labelled and shipped. Nothing in the code resolves a single one of those references. And 102 real filings now sit beside it in data/real/ — testimony, orders, tariff compliance sheets, quarterly reports — of which two files are parsed by anything at all, and those two are parsed as plain text.

4. Human-in-the-loop review — PARTIAL

The review loop itself runs. A refusal becomes an escalation carrying a reason code and the reason in plain words, and the queue shows the reason and never the statement it withheld. A person upholds or disputes it, a dispute without an explanation is refused and nothing is written, and both outcomes append to the hash chain. Steer directives are rows with an issuer and a time rather than a setting overwritten in place. There is a review centre over the top.

Routing exists now, and the queue screen is the last place to hear about it. app/state/routing.py walks an escalation to the claim, the claim to the change, the change to the company obligations it bears on, and the obligation to its owner — and every step of that walk can refuse. A refusal code per fix — the obligation has no owner, the owner's account is suspended, two obligations name two different people, nobody confirmed the mapping this name rests on — plus ROUTE_PENDING_ACCEPTANCE, which says an owner was invited and has not accepted yet, and is carried as data rather than as a sentence so a screen cannot render “waiting on Priya” and “waiting on Priya, invited two days ago” the same way. It never guesses a default assignee, because a wrong assignment looks handled, leaves the queue and sits on a desk that will not act on it. Escalation carries assigned_to_user_id and assigned_at, written together or not at all. None of that reaches /escalations. The queue template contains the string “assign” zero times; it still lists every unresolved refusal in id order, with a text box for a reviewer's name. Clarke can be asked who owns a duty and what is on the shared queue. A person looking at the review screen cannot see it, and cannot route anything from there.

Annotation stops one level above where it is wanted. record_note() in app/chat/tools.py writes a free-text note against a project, through Clarke, and there is still no route that writes one against a claim or a passage. The shape exists in the state layer — ResearchTurn carries a nullable claim_id, and add_turn() refuses a claim this company cannot read — and the seed uses it, so the screens render notes attached to claims that they have no form to create. Two things the note path concedes in its own docstring: it is recorded with author kind system, not analyst, because what reached the column is what Clarke decided the person meant; and it is gated by no permission at all, because the product defines no code for writing a note. The free text a reviewer can write through the running product is a project note, the reason on a disputed refusal, and a steer instruction. And the approval control reached no screen for a day. app/auth/policy.py::can_approve is real work: four gates, the fourth reading authorship out of the audit chain rather than a column, with a demo waiver that writes approval.waived under its own action code (ADR-018, ADR-019). It now has one caller — app/web/views/actions.py::decide, ADR-091 — and the reason it took a whole screen rather than a line is the interesting part: there was nowhere in the product to propose an action, so the gate had no decision under it. Both resolve routes take a reviewer's name typed into a text box, check no permission, and let any signed-in person close any escalation. The control is proved in the module and absent from the product, which is the same defect a citation that verifies in tests and not on screen would be.

“Override” has two readings here. A reviewer may dispute a refusal, and the dispute is recorded with their reason. A reviewer may not make an unverified claim publish. Resolving an escalation moves nothing into state: the claim stays withheld whichever way the decision goes, and the coverage counts do not move. That is a deliberate position, not a missing feature. A verifier a person can talk past is a verifier the next auditor discounts, and the one hard promise this product makes is that anything shown as fact re-read cleanly a moment before it was shown. If a customer needs publish-over-refusal, it should arrive as a separate, differently named action that records the assertion as that person's and not the system's — never as a flag on the existing one.

5. Auditability — PARTIAL

The chain is built and it is the second-strongest thing here. Every decision writes an AuditEvent through one function, hash-linked per company and gapless from 1, so a deletion shows as a gap and an edit breaks the chain. A before_flush guard refuses any UPDATE or DELETE from application code, which stops mistakes; the SHA-256 chain catches a row rewritten out of band, which the guard cannot. Attribution — who, which session, which address — is hashed inside the digest rather than stored beside it, and because adding those fields changed what gets hashed, every row states its own scheme and verification dispatches per row (ADR-017). Old hashes are the evidence, so they are never recomputed.

Measured against their exact wording, three parts of it are missing. What was retrieved is not logged. The chain records decisions, not reads, and that is a stated position rather than an oversight — app/auth/policy.py depends on it when it reads authorship out of the chain. So when Clarke searches the record on somebody's behalf, the question and the answer land in the chat transcript and no row lands in the chain. What the chain holds instead is what was ingested, with a SHA and a full-span citation, which is a different and narrower fact. A regulated buyer who asks “what did this tool look at before it told you that” gets an answer from a table that is not tamper-evident. With what confidence arrives as prose: the pipeline writes alignment confidence 0.50 into the reason string, so a person can read it and a query cannot filter on it. And rollback reaches no screen: in app/state/rollback.py, revert_event() writes a reversal row naming the event it takes back, reopens the escalation, and keeps both rows in the chain, guarded by 38 tests in tests/test_rollback.py — and no view calls it, the same shape as the approval gate and the ingest-hash check. When and from which source are real: an aware UTC timestamp on every row, and the cited span as version_id:start:end. The chain is the mechanism their requirement asks for; it is not yet carrying everything the requirement names.

Every table in the schema has a retention window, and erasure means something narrower here than a buyer will assume. SCHEDULE in app/state/retention.py gives every table in the schema a window, the column its clock is measured from, a reason, and a dotted path to the code that carries it out; tests/test_retention.py refuses a table with no rule and resolves every mechanism by import rather than believing it. The window on audit_events is never. The chain is append-only twice over and no purge reaches it, so a subject row is deleted while the audit row naming it survives, pointing at an id that no longer resolves. What a reader of the log can still learn about a deleted record: that a record with that id existed, what kind of thing it was, when each decision about it was taken, who took it, from what address, and the reason they gave. What they cannot learn: what the record said — the words of a chat turn, the text of a complaint, the address a shared link was opened from.

Where the personal datum is the actor or the reason, no purge reaches it at all. record_event stores subject_id, actor and reason verbatim. A failed sign-in records person:<address> as the actor and, with no account matching, that address again as the subject, and it stays there for good. An invitation's audit row quotes the invited address in its reason, and purging the invitation leaves the line standing. Tests pin both, because a limit nobody writes down is a limit the buyer finds instead. The module refuses to call that erasure, and so does this document. A regulated buyer's procurement team asks this first, which is why the answer sits here rather than only in the code. A buyer who needs deletion to mean deletion — because their regulator says so, or their own policy does — needs a different product. That is the same trade the section above makes about the verifier. A record a person can edit on request is a record the next auditor discounts, and the record is what this product is bought for. Two settings stand between the daily job and a deleted row, and they are deliberately not one: STRATA_JOBS_ENABLED starts the loop at all, STRATA_JOBS_RETENTION_DELETE arms the destructive path, and without the second the run reports what it would have removed and removes nothing.

What the submission has to cover, in plain English

The brief names eleven areas. The names are industry words and several of them promise more than they say, so the middle column defines each one in the words you would use to a colleague. The third column says where the build actually stands, and it was filled in by reading the code, not by reading the plan.

Eight of the eleven are built and tested. Three are not what the name suggests, and they are listed here at the same weight as the eight. That is ADR-022 — the rule that every synthesis states what it withheld — applied to our own document. Five of the eleven rows named a control that was written, tested, and called by nothing in app/ — the ingest-hash check, can_approve, revert_event, propose_changes, and ten of the fifteen permission codes. can_approve is off that list as of ADR-091; the rest stand. Each is named in its own row, because a capability that lives in a module nothing calls is not visible in the product, and that distinction is what this table is for.

Ingestion Getting a filing into the system: read the document, store its text, and remember exactly which characters came from where. Built and tested. app/ingestion/ingest.py stores the raw text byte for byte, a SHA-256 of it, and paragraph-level passages each carrying its exact start and end offset into that text. Nothing rewrites, trims or re-encodes the source, because an edit here would silently invalidate every citation minted against it. tests/test_ingestion.py asserts every passage offset slices to its own text and that the stored bytes are unchanged.

One thing the word oversells: it is handed a string, not a file. There is no PDF reader, no HTML reader and no upload screen — the seed reads .txt from data/, and scripts/ingest_real.py reads .txt from data/real/ beside a provenance JSON that a person's retrieval run wrote. python-multipart is pinned for an ingestion screen that does not exist, and grep -rn UploadFile app/ returns nothing. The normalization layer is built for PDF-shaped text (soft hyphens, hyphenated line breaks, ligatures) and is tested against it, so the hard half of PDF handling is done; the file-reading half is not.

What the real corpus added: a version now carries the address it came from, who filed it and on what day, and the URL goes through the same check a template uses, so a provenance file naming a javascript: address is refused at ingestion rather than at render. That is the one thing a regulatory reader wants from a citation — not our text, theirs.
Version diffing A proceeding gets filed, amended, then rebutted. Diffing works out what changed between two versions, not just that something did. Built and tested. app/diff/engine.py is a pure function: two passage sequences in, typed changes out, no model, no network, no clock, no randomness. It reports added, removed and modified with a reference on each side, plus an alignment confidence. The corpus's five labelled edits are all found at the manifest's own offsets. The known weakness — a section renumbered and relocated looks like a deletion plus an addition — is handled rather than hidden: confidence is capped at 0.5 when the leading section label disagrees, so a restructure escalates instead of presenting itself as a settled match. tests/test_diff.py, plus test_every_labelled_change_in_the_manifest_is_found_by_the_diff.
Evidence-linked extraction Pulling out statements ("the notice period went from 30 days to 60") and tying each one to the exact spot in the source it came from. The linking is real. The extraction is written and nothing calls it. A model does run in this repository now, and it runs in exactly one place a user can reach: Clarke, the assistant, through app/chat/agent.py — and only where somebody set ANTHROPIC_API_KEY. Without one, transport_from_environment() returns None and the assistant says "this deployment has no ANTHROPIC_API_KEY" rather than answering from memory, which is the fallback announcing itself instead of pretending (best-practices §26). The extractor is app/interpretation/propose.py — it asks Claude what changed between two versions, hands the model a closed list of permitted actions dispatched from the version's own draft-or-final status (ADR-005), binds every proposal to a (version_id, start, end, quote), re-reads each one through the verifier, and repairs nothing: a proposal two characters off its quote is withheld, not nudged into place, because snapping offsets would make the gate a formality. grep -rn propose_changes app/ scripts/ finds no caller. The limit the proposer states about itself, in its own docstring: this path has never run against the real API, because nobody here has held a key. Every test drives a fake through an injected transport. What is proven offline is the gate; what is unproven is anything only the endpoint can answer.

What is real is the half the product's thesis rests on: every claim carries version, start offset, end offset, quoted text and occurrence index, and a claim whose citation fails genuinely refuses to assert itself — it has no statement field to leak. So this is the evidence link enforced end to end, with a seeded corpus standing in for the extractor and the extractor sitting beside it, tested and unwired.
Company-context data model The system's picture of your company: which obligations you carry, who owns each one, which proceedings touch you. All three parts are state now, and the demonstration does not show them. "Which proceedings touch you" was always real: Proceeding → Change → Claim, with projects, questions, findings, knowledge items, takes and deliverables around them, all scoped by company. The other two arrived with Obligation and ChangeObligation in app/state/models.py: a duty carries a title, a project and an owner_user_id that resolves to an account rather than a name typed in a file, and a change is mapped to the duties it bears on. app/state/routing.py reads both, which is what gave reviewer routing something to route to.

Nothing seeds them on the path a reviewer takes. make run calls app/seed.py, which loads the corpus and the accounts and writes zero obligations — measured, by seeding a scratch database and counting the rows. The eight duties in data/company_context.json reach the database only through scripts/seed_demo_gaps.py, which neither make run nor deploy/entrypoint.sh calls. So a reviewer who follows the README sees the owner-handoff feature with nobody in it, and the live site shows it only because that script was run there by hand. The script's own docstring says a freshly seeded workspace had 26 tables with rows and 16 without, and that no test asked whether the demo had content rather than capability.
Citation verification Before showing a statement, go back to the stored source and check the quote is really there, in that spot. If it is not, do not show it. Built, tested, and visible in the product, with one check that stops at the module. This is the depth area (ADR-003). The path a rendered claim takes is verified_claims() in app/state/claims.py: it re-reads the stored source at the cited offsets on every request — never a stored verdict — and refuses an empty span, an inverted span, offsets past the end of the source, a quote that does not match, a quote that appears more than once without naming which occurrence it means, and a version this company cannot read. It pairs each claim with the text of the version the claim names, from a map keyed on version id and built through the tenant chokepoint, so a citation filed against the wrong version cannot pass on words that happen to sit at those offsets in another one.

The hash check is not on that path. verify_citation_for_version() hashes a version's stored text and refuses when the digest disagrees with the one ingestion recorded. Nothing under app/ calls it — tests/test_verification.py does, and the function's own docstring says the hash check "does not yet run in production". So an edit twenty characters away from a cited span leaves a citation into that version verifying on screen while the stored hash disagrees with the stored text. Measured under Retrieval with citations above rather than inferred. A capability that lives in a module no screen calls is not visible in the product.

Visible, not buried: /changes/CHG-v1-v2-003 carries two claims. One renders with a chip that opens the source and marks the exact span. The other is a deliberate misquote at real offsets and renders as "No claim made", with what was quoted set against what the source really says. Guarded by tests/test_verification.py, test_occurrence.py, test_pdf_text.py, test_normalize.py and test_claims.py.
Confidence and escalation Deciding how sure the system is, and what happens when it is not sure enough: hand it to a person instead of guessing. Built and tested. Every claim carries a confidence in integer basis points, and a claim below the threshold is withheld with its own reason code rather than shown. A citation failure beats low confidence to the reason, so the more specific problem is the one reported. Alignment confidence on the diff does bite today: a restructure is capped at 0.5 and escalates.

The claim threshold ships at 0, so no claim is currently withheld for confidence alone — every withholding in the demo is a citation failure. That is deliberate: there is no evidence yet for where the line sits, and a number chosen to look rigorous is worse than an honest zero. The mechanism is built and tested (test_low_confidence_withholds_once_a_threshold_is_configured) so setting it is configuration, not a code change: MIN_CONFIDENCE_BP in app/state/claims.py reads STRATA_MIN_CONFIDENCE_BP and defaults to "0", and .env.example names the variable. Calibration is an open question in the decision log, not a solved one.
Reviewer routing Sending the uncertain item to the right person, not just onto a pile. Built, and the queue screen has not heard about it. Escalation now carries assigned_to_user_id and assigned_at, written together or not at all, with an index for "what is on my desk" and for the unassigned pile. app/state/routing.py resolves an owner by walking escalation → claim → change → obligation → owner, refuses with one of fifteen coded reasons when any step cannot answer, and re-derives the reason at read time so that suspending an owner this morning changes what the queue says this afternoon. It refuses to pick a default assignee, on the argument that a wrong assignment looks handled and a refusal stays visible.

Where it actually runs. Clarke reads it — obligation_owner and open_escalations report who holds what, and name the duties nobody holds. Revoking an invitation un-routes the escalations that invitation was holding, and that path does reach a screen. Nothing else does. invite_owner_for_escalation() has no caller outside tests. /escalations still lists every unresolved refusal in id order with no owner column — grep -c assign app/web/templates/review.html returns 0 — anyone signed in can resolve any of them, and the resolve form still takes a reviewer's name typed into a text box rather than the signed-in person.

The approval half has moved, and not on this screen: app/auth/policy.py::can_approve enforces segregation of duties off the audit chain, and ADR-091 gave it the screen it was missing — /actions, where a proposed action is approved or rejected. Escalation routing is still not surfaced in the queue, which is the gap this row is about.
Audit history and rollback A record of every action and who took it that cannot be quietly edited, plus the ability to undo a change and go back to an earlier state. The history half runs. The undo half runs only in tests.

History: built and tested. Every decision writes an AuditEvent through one function, hash-chained per company. A before_flush guard blocks any UPDATE or DELETE from application code, and the SHA-256 chain catches an out-of-band rewrite — an edited reason and a removed row are both detected as tampering by tests/test_audit.py. Attribution (who, which session, which address) is hashed inside the digest, and because that changed the hashed field set, every row states its scheme and verification dispatches per row (ADR-017); the old hashes are the evidence, so they are never re-hashed.

Rollback: written, tested, and reaching no screen. In app/state/rollback.py, revert_event() writes a reversal row that names the event it takes back, reopens the escalation that event closed, and leaves the original row untouched so the chain verifies over both; the pointer sits inside the digest, so re-aiming a reversal turns the chain red. 38 tests in tests/test_rollback.py pass. No view calls it — the only rollback hits under app/web/ are four session.rollback() calls, three in feedback_review.py and one in shares_admin.py, none of which is this. So the undo exists in a module and not in the product. The module also draws the line the product needs: reverting a decision restores what that decision changed and cannot make an unverified citation verify.
Evals A repeatable measurement of whether the thing is actually right, producing numbers you can defend when challenged. Built and tested. make eval prints five metrics and one observation, each stating what it measures, how it is computed, and the threshold it has to clear, scored against data/manifest.json whose offsets were produced by a separate script and verified against the bytes. The observation, diff noise, is measured and deliberately not scored, because a number nobody can fail is a report and should not be dressed as a gate. It exits 1 when any blocking metric fails. It calls no model, opens no socket and touches no database, and a test asserts each of those. It prints raw counts with denominators and refuses a percentage below a sample of ten, so a corpus of five labelled changes cannot be reported as a rate.

The limit is printed in the scorecard rather than left to be found: it scores the deterministic spine only, so a green run says nothing about model behaviour — and now that a model does run in the product, that limit is larger than it was this morning. It is measured against the synthetic corpus alone. The 102 real filings are not scored by anything, because scoring them needs labels nobody has written; the one exception is the Kentucky pair, where the filer published a marked-up copy, and using it as an answer key is written down as work rather than claimed as done.
Data isolation One customer's data can never be read by another: not by accident, not by guessing an id. Built and tested. One chokepoint, app/state/queries.py, and a read with no company id is refused rather than answered — a query that returns everything when the caller meant nothing is how isolation fails in practice, and it fails silently. Passage deliberately carries no company id; tenancy is joined from the version that owns it, so two columns cannot drift apart. That join was defect #1 in docs/.ai/findings.html and is now guarded by five tests. Another tenant's version and a version that does not exist return the same refusal, so an attacker cannot use the answer to enumerate ids. Cross-tenant tests run in isolation, passages, claims, review, identity, verification and the assembled application.

The limit: this is enforced in the application, not by the engine. SQLite has no row-level security, so the guarantee is a chokepoint plus tests rather than a database that refuses. Postgres with RLS is the named reversal, and SQLAlchemy makes it a configuration change.
Security Logins, roles, permissions, sessions, how passwords are stored. Built and tested. Passwords through hashlib.scrypt, memory-hard, with the cost parameters written on each user row and read back at every verify, so raising the cost later locks nobody out (ADR-015). Three system roles and fifteen permission codes as one grid, where the control is the row that is missing — the analyst holds no action.approve (ADR-021). Sessions are server-side rows holding only a SHA-256 of a 256-bit random token, twelve-hour fixed lifetime, revocable the moment an account is suspended, cookie HttpOnly, SameSite=Lax and Secure (ADR-020). Five failed attempts lock an account. Every authentication and authorisation event joins the one audit chain rather than a second log (ADR-016). An administrator can provision an account by invitation, on a 24-hour token, and revoking one un-routes whatever it was holding.

Ten role templates, and none of them is in the database. scripts/seed_roles.py names ten roles taken from titles this repository can point at — the interconnection, load-forecasting and system-operations owners in data/company_context.json, and the Analyst II, Regulatory Counsel, VP of Pricing and Planning and Deputy Director who signed filings in data/real/. Seniority is not a permission: a Director of Load Forecasting and a Director of System Operations approve different things. No template holds both action.propose and action.approve, not because a small team may not, but because a default must not hand it over in silence. Two limits: the script validates and prints, it writes no Role row, so the three system roles are still all the database has; and the templates are meant to be copied and never edited, because a role called "analyst" that one company has quietly changed means something different on every screen and in every ADR that names it.

Three downgrades, each of which announces itself rather than hiding: the seven demo accounts share a password that is printed by the seed and shown on the login page; STRATA_APPROVAL_MODE=DEMO_SELF_APPROVAL waives segregation of duties and writes approval.waived into the chain under its own action code, so a waived separation can never be read later as a clean approval (ADR-019); and the Secure cookie flag comes off for plain http to this machine only, which the login page prints on the page. Absent, not deferred: no SSO, no second factor, no password reset, no rotation, no breach-corpus check.

And the grid enforces five of its fifteen codes. Found by looking for the callers rather than the module. policy.require() now runs on workflow.manage in admin.py, on user.manage in users_admin.py, shares_admin.py, feedback_review.py, app/state/invites.py and the integrations registry (SOURCE_REGISTRY_PERMISSION, which is the string user.manage until a source.manage code lands), on project.create when Clarke opens a project, and on claim.read or change.read when somebody mints a share link. That leaves ten codes — including every one an analyst uses to do the actual job, action.propose, action.reject, escalation.resolve, steer.issue, knowledge.write, threshold.set, audit.read — as grants the product stores and audits and checks nowhere. The sign-in middleware in app/web/deps.py resolves a session and checks no permission, and says so in its own docstring, so a signed-in person holding no role still reaches every screen it lets through. action.approve cannot be passed to require() at all, by design; can_approve() answers it, and ADR-091 gave it its one caller, which also put action.propose and action.reject on a screen for the first time. Sessions, password hashing, lockout and invitations do run on the screens; two thirds of the grid does not.

Why this table is in the market document. Because the gaps are market facts, not engineering trivia. The extractor exists and nothing calls it, so the demo still shows a correctness engine rather than an extractor, and the sentence "we use a model" has to be said with the caveat attached. Routing resolves an owner and no screen shows the answer, so the "who reviews this" half of the pitch is a running feature a buyer cannot see. And a control that sits in a module nothing calls buys a buyer nothing, whatever the tests say — which is where the approval gate, the ingest-hash check, the claim proposer and revert_event all sit today. Each changes what can be claimed.

One shape keeps recurring, and it is a discipline problem rather than a list of bugs. Four times now a capability has been built, tested and left unwired, and each time the tests stayed green because a test proves a module works, never that a product uses it. The counter-measure the repository already has is tests/test_app_wiring.py, which derives what it checks from app.routes rather than from a list somebody maintains. There is no equivalent for a state module, and none at all for prose.

The market, and who is in it

The category. Regulated enterprises — companies whose obligations change not because they choose to change them, but because a government body issues an order and the clock starts. That category is wide: utilities, banks, insurers, pharma manufacturers, telecoms, pipeline operators. Strata does not target the category. It targets one beachhead inside it, for the same reason ADR-001 names one user instead of a persona list: a product built for "regulated enterprises" is a product built for no one.

The beachhead. Investor-owned utilities and independent power producers. Both live under a regulatory structure with a specific shape: a company's obligations are set proceeding by proceeding, docket by docket, at one or more state public utility commissions and, for anything that touches wholesale power or interstate transmission, at FERC. A multi-state holding company does not run one open docket — it runs one per jurisdiction it operates in, each on its own procedural clock, each amended independently. That structure, not a market-size figure, is the argument for why this is hard: the unit of regulatory obligation is fragmented by design, and no single filing tells a company everything it now owes.

Why not name a market size. A defensible TAM number needs a source — utility count, average regulatory-affairs headcount, spend per docket — and none of that is sourced here. This document reasons about the shape of the market instead, and leaves the size as an open question for the go-to-market plan to answer with real numbers.

Why now

Three forces are moving at once, and they compound rather than add.

Sourcing note. The specific claims below — FERC Order No. 2023 and the interconnection backlog it addresses, and data-center-driven load growth — are asserted from industry knowledge, not sourced here. They are probably true and they matter to the argument, so this document flags them rather than deleting them, as it flags the missing market-size figure above.

AI-driven load growth. Large new electricity demand from data centers is pushing utilities to file for generation, transmission, and rate changes on a schedule utilities have not run at in decades. Every one of those filings opens or amends a docket. More dockets per utility means more proceedings a regulatory-affairs analyst has to track in parallel, each with its own version history.

Interconnection reform. FERC's interconnection rulemaking (Order No. 2023 and the state-level proceedings that followed it) rewrote how generation projects join the queue, specifically because the prior process built a backlog FERC's own rulemaking record describes as multi-year. Reform of that scale does not land as one final rule — it lands as a sequence of orders on rehearing, compliance filings, and state tariff amendments, each one a new version of a proceeding an IPP has to re-read against its existing project queue.

The pace of energy-transition rulemaking. State clean-energy targets, integrated resource planning cycles, and the state-level implementation of federal incentive programs are producing more proceedings, not fewer, and each proceeding revises more often before it settles. The volume of change is rising faster than regulatory-affairs headcount is rising to track it — that gap is the market opening, and it is a structural one, not a one-year spike.

The compounding effect. None of the three forces is new by itself. What is new is that they land on the same desk at the same time: more proceedings, more amendments per proceeding, and a workforce of analysts whose headcount has not scaled with either. A tool that only helps with one force helps less than the timing suggests. A tool that speeds up reading a proceeding regardless of which force generated it is the one that matters now.

Buyer versus user

The user (per ADR-001). The regulatory-affairs analyst who reads the docket, works out what changed, and tells the business what it must do. This is who the product is built for and who the PRD is written to.

The buyer. Almost certainly not the same person. The analyst rarely holds a software budget. The likely buyer is the person the analyst reports to — a VP of Regulatory Affairs, a chief compliance officer, or general counsel — someone who is measured on whether the company missed a deadline or acted on an order that later got vacated, not on how many hours the analyst spent reading. That is a hypothesis, not a finding: H1 in user-research.html asks a version of this question and no interview has yet confirmed or falsified it.

Why the difference matters, not just as sales trivia. The user is sold on time saved and trust — does the tool read the docket correctly, and can they verify a claim without redoing the work themselves. The buyer is sold on risk — can the company show, if a regulator or an auditor asks, that a specific order was seen, assessed, and acted on within the deadline, with a record of who reviewed it. Those are different pitches with different proof. A demo that only shows the analyst's daily win risks stalling at the buyer's desk; a pitch that only shows the audit trail risks a tool nobody in regulatory affairs actually opens.

Open. Whether the buyer is regulatory affairs' own budget or sits inside a broader compliance or legal software line is unconfirmed. It changes who gets pitched and what the tool gets compared against, and it is exactly the kind of question a real conversation answers in five minutes and speculation does not.

Incumbents and adjacent tools

Four categories already sit near this problem. Each does something real. None does the specific join Strata is built around: an exactly-cited change, in a specific proceeding, mapped to this company's own obligations and projects, with an action and a reviewer attached.

CategoryWhat it doesWhere it stops
Regulatory change management / GRC platforms Watch regulatory feeds and dockets, tag new filings by topic or jurisdiction, alert a subscriber when something posts, sometimes map a tag to an internal policy. The alert is the product. It does not diff the new version against the last one, does not distinguish a draft comment period from a final order at the data-model level, does not quote the exact passage that changed, and does not know this company's specific obligations or projects — only the topic tags an administrator configured. The interpretation work ADR-002 names as the expensive part starts after the alert, not before it.
Trade and supply-chain compliance suites Screen transactions against denied-party and sanctions lists, classify goods against tariff schedules, check a shipment or a counterparty against a fixed, structured ruleset. Built for a different shape of problem: a lookup against a ruleset that changes occasionally, not an evolving proceeding that changes on its own procedural clock and has to be read as prose, not matched as a code. The engine is optimized for structured lookups; a docket amendment is unstructured text with legal consequence, and that is the harder problem this category was never built to solve.
Legal research tools Search regulatory and case text, track citations, surface related filings and headnotes, support a lawyer building an argument or a memo. A search tool, used per query, not a maintained state. It has no notion of "this company's obligation register" or "this company's open projects" to map a result against, and nothing persists between searches unless the user builds that structure themselves outside the tool. It answers "what does the rule say" well; it does not answer "what does this mean for us" at all.
Law firms, as a service Read a proceeding, apply legal judgment, write a memo interpreting what changed and what it means, billed by the hour. The judgment is often good. The cadence is not: a memo takes days, and the per-hour cost means firms get engaged for the proceedings that already look material, not for the routine amendment that turns out to matter on closer reading. That selection effect is exactly where coverage gaps open — the amendment nobody thought worth a legal review is the one that gets missed, and no one finds out until it is binding.
Categories, not named competitors. The rows above describe what each category of tool does in general, not a specific vendor's current feature set; this document has no sourced, current facts about any named product and states none. If a specific incumbent has already closed part of this gap, that is exactly the kind of thing a user interview or a competitive trial would surface, and it belongs in user-research.html and the ADR log, not guessed at here.

Where the wedge sits. Between the alert and the memo. The regulatory change management category tells you something moved; the law firm tells you, slowly and expensively, what it means. Strata's bet is the middle: an exactly-cited account of what changed, machine-mapped to this company's specific obligations and projects, fast enough to run on every proceeding amendment rather than only the ones that already look expensive — and honest enough, through confidence-gated escalation (ADR-006), to say when it does not know rather than guess.

Why this is defensible beyond being first

Not defensible. The model call itself. Any well-funded competitor can wire an LLM to a docket feed by next quarter. If the pitch for defensibility rests on having used AI first, it is not a pitch — every incumbent in the table above will add a model to their product this year regardless of what Strata does.

The floor, not the moat — the correctness engine. Citation verification against exact source offsets (ADR-003) and deterministic diffing before model interpretation (ADR-004) are necessary, not sufficient. They are table stakes: the work a buyer has to see before trusting the tool with anything else. A competent team rebuilds both in a few weeks — docs/future-enhancements.html says so plainly, and this document agrees rather than argues around it. These earn the right to be trusted. They do not keep a competitor out.

The moat — the obligation graph and the multi-jurisdiction taxonomy. The durable advantage is the mapping between how a regulator words a requirement and how a specific company words its own obligations, built proceeding by proceeding, jurisdiction by jurisdiction, for one specific company (ADR-002, T9). That mapping compounds per customer: a multi-state holding company's taxonomy gets more accurate and more entangled with its own operations the longer the tool runs, and it cannot be bought — a competitor starting today has to rebuild it customer by customer, not download it. The same logic makes best-practices.html's principle that "a derived corpus migrates all at once" true here: once the taxonomy is load-bearing, removing it is not a vendor swap.

This moat does not exist yet. At launch there is no accumulated obligation graph and no multi-jurisdiction taxonomy. There is a working prototype, an Obligation table with eight rows a script can seed from one invented company's own file, and 102 real filings from eight commissions that nothing has mapped to any obligation at all. A table is not a graph and a corpus is not a taxonomy. The moat is a direction the product is pointed at, not an asset it holds today. It has to be earned proceeding by proceeding, customer by customer. Claiming it now, before a single customer's obligations have been mapped, would be the same overreach ADR-003 refuses to let the product itself make.

A further candidate — the audit trail becomes the record of record. If a compliance officer starts pointing to Strata's project state as the answer to "what did we know and when," removing the tool stops being a vendor swap and starts being a legal-risk decision. That lock is stronger than the floor, but slower to earn even than the taxonomy — it requires a customer to trust the tool with exactly the kind of record an auditor might ask for, and no 48-hour build can manufacture that trust.

Open. Nothing past the floor is proven. The working prototype demonstrates the floor — that the correctness engine works and can be shown working. It demonstrates nothing about the obligation graph, the taxonomy, or the audit trail, which need real usage over quarters, across real proceedings, to become true rather than merely plausible.

Expansion path, from one vertical outward

Step 0 — where the build stands. One user, one sector: the regulatory-affairs analyst at an investor-owned utility. This is deliberate narrowing per ADR-001, not the ceiling of the ambition.

Step 1 — same regulator archetype, adjacent players. Independent power producers and energy retailers sit under the same state-PUC-plus-FERC structure as utilities. The proceeding shape, the draft-versus-final distinction (ADR-005), and the citation engine transfer with little change; the obligation taxonomy shifts because an IPP's obligations run through interconnection agreements and power-purchase contracts more than through rate cases. Cheapest expansion: new obligation vocabulary, same engine.

Step 2 — adjacent regulator archetype. Telecom, regulated by the FCC and state utility commissions in a structurally similar docket-and-order pattern. The diff and citation engine still transfers; the obligation taxonomy and the judgment of what counts as material both need rebuilding, because "material" in a telecom tariff filing and "material" in a utility rate case are not the same question answered with the same evidence.

Step 3 — further out, and a real schema lift. Banking and insurance compliance, where rulemaking has a different shape entirely — rule-and-comment-period rather than docket-and-amendment — and pharma, where the trigger is often guidance rather than an order. The correctness engine is domain-general by design (ADR-003, ADR-004 do not reference energy anywhere in their logic); the extraction and materiality judgment are not, and treating them as if they transferred for free would repeat the exact mistake ADR-006 exists to prevent — presenting an untested judgment as settled.

The constraint that governs every step. Expansion is gated by repeating the discipline in user-research.html for the new vertical, not by copying the schema and assuming it holds. A second vertical earns nothing if the first one's hardest lesson — talk to the user before believing the taxonomy — gets skipped the second time because the roadmap wants to move fast.

What would have to be true for this to be a large business

The buyer needs a felt cost, not an inferred one. A VP of Regulatory Affairs or a general counsel has to be able to point to what a missed deadline or a wrongly-timed action actually cost the company — in a rate case, a penalty, or a compliance filing that had to be redone. Utility rate cases plausibly carry costs like this; whether the buyer actually reasons in those terms, or budgets against them, is unconfirmed and is exactly the kind of thing H1 and the "when were you last burned" interview question in user-research.html are built to surface.

The escalation queue has to stay usable at scale, not just in the demo. ADR-006's own trade-off names the risk directly: "a queue nobody empties is its own failure." The 48-hour build can show the queue working against a synthetic corpus of known size. A business depends on it staying fast enough to clear across many customers' real proceedings, which is an operating question the eval harness starts to answer and does not finish answering: it scores correctness on a fixed corpus, and says nothing about a queue's throughput under load.

Usage has to be continuous, not a one-time purchase. State PUC dockets run on an ongoing procedural calendar — proceedings do not end when a company buys the tool. If that reasoning holds, the product should see recurring, not one-time, use, which is what a subscription business needs. This is inference from how dockets work, not evidence from a customer, and should be labeled as such until a real account confirms it.

The engine has to prove general by actually going to a second vertical. Step 1 in the expansion path above is the test. If moving from utilities to IPPs takes a rebuild rather than a re-tag, the defensibility argument for candidate 1 above weakens considerably — the correctness engine would be general in theory but sector-specific in practice, and that gap only shows up by actually doing it.

The sale has to land inside an existing budget line, not compete with a hiring decision. Regulatory-affairs teams are more likely to get a tool budget than a net-new headcount request approved in the same cycle. A pitch that reads as "hire fewer analysts" invites resistance from the exact user the product depends on for adoption; a pitch that reads as "the analyst you have covers more ground" does not. This is a positioning judgment made now, without a buyer conversation to test it, and it should be checked against the first sales conversations the company has, not assumed permanent.

What is not yet true. No user interview has been conducted. No buyer has been spoken to at all — the interview plan targets analysts, not the budget holder above them. No pilot customer, named or anonymous, exists. The eval numbers do now exist and they measure the deterministic spine against an invented corpus, which is a smaller claim than the sentence "we have evals" makes: nothing scores the model, and nothing scores the 102 real filings. A large business needs all of that before it is a large business rather than a well-argued idea; this document is the argument, not the proof.
