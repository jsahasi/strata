Technical Design Document

Strata — citation-grade regulatory change intelligence. How the hard bet is built, with the alternative considered and the trade-off accepted at every step.

Written 2026-08-03, before implementation, per the project convention (TDD before code for anything with logic worth trusting). Kept current as the build changes — a TDD that stops matching the code is worse than none, because it tells the reader a false story with confidence.

How to read this. Every section states what was built (or, for pieces not yet written at time of drafting, what will be built and why), the alternative rejected, and the trade-off accepted. Where a number is not yet known — because the eval has not run, or the threshold has not been tuned — this document says so rather than filling the gap with something plausible. A guess dressed as a result is exactly the failure this product exists to prevent in its own domain; it would be strange to allow it here.

System overview

Two version-controlled corpora feed one pipeline. A proceeding — an external regulatory docket — arrives as successive document versions, each tagged draft or final. A company context — obligations, projects, documents, written in the company's own words, never the docket's — sits beside it. The pipeline turns a new version into: what changed (deterministic), whether the change matters (model, evidence-linked), what it touches in the company context (retrieval plus model, confidence-scored), and what to do about it (a routed action). Every factual claim the pipeline makes — a change happened, an obligation says X, a change affects obligation Y — carries a citation, and a citation that does not verify against the stored source is never shown as fact.

The system is a single FastAPI service over SQLite (ADR-007), server-rendered, with one background-eligible stage: model calls. Everything upstream of a model call — text extraction, segmentation, diffing, offset bookkeeping — is deterministic, unit-tested against known answers, and has no failure mode that involves the model being wrong, because it never asks the model anything.

1. Ingestion & passage segmentation

Design

A document version is ingested once and stored as immutable raw text plus a SHA-256 of that text (document_version.source_sha256). Versions are never edited in place — a correction is a new version, never a mutation, because every downstream offset assumes the text under it cannot move. Ingestion then segments the raw text into passages: the unit everything else — diffing, citation, extraction — operates on.

Segmentation splits on structural cues native to regulatory drafting: numbered/lettered clauses (§4.2, (a), Ordering Paragraph 3), blank-line paragraph breaks, and heading patterns. Each passage is stamped with (document_version_id, seq, char_start, char_end, structural_ref), where char_start/char_end index directly into the stored raw text — not into a re-flowed or re-normalized copy — computed in a single pass over the text so a passage's offsets can never drift from a later re-parse.

PDF extraction is itself a place error enters and is treated as its own tested stage, not folded into segmentation: page headers/footers, hyphenation across line breaks, and column reflow are resolved once, at extraction, before any offset is computed. Everything downstream trusts the extracted text as the source of truth for that version — which means an extraction bug is invisible to every later stage. This is the ingestion pipeline's single largest correctness risk and it is a deterministic-code risk, not a model risk; the mitigation is a fixed extraction library version and golden-file tests on the synthetic corpus's known text, not a confidence score. The golden-file tests prove only that extraction stays stable against the corpus it was written for. The synthetic corpus has no multi-column layout, no scanned exhibit, no ligature beyond a handful chosen for the normalization tests (§5), and no header/footer bleed across a page boundary — the actual artefacts real regulatory PDFs carry. The mitigation is real for what it tests and untested for what it does not; that gap is named again in §14.

Alternatives considered

OptionRejected because
Fixed-size token windowsEven chunking is easy to implement but ignores document structure — a citation span routinely cuts a sentence in half, and a diff routinely straddles two unrelated clauses.
Sentence-level segmentation (NLP splitter)Finer citation precision, but multiplies passage count 5–8x, which multiplies the number of alignment decisions diffing must make (§2) and the number of low-confidence edge cases that can each independently escalate.
Whole document as one segmentNo segmentation cost, but every diff and every citation becomes page-scale — useless for judging materiality and useless for a reviewer trying to see what changed.

Trade-off accepted. Paragraph/clause-level segmentation is coarse when a long paragraph contains one small change — the passage-level offsets bracket the whole paragraph, not the sentence. Diffing (§2) works at character granularity within an aligned passage pair precisely to compensate: the passage is the unit of alignment, not the unit of citation precision.

2. Version diffing (ADR-004)

Design

Diffing is deterministic code, in two steps, and the model is not part of either. Alignment matches each passage in version N to its counterpart (if any) in version N+1: an exact hash match on normalized passage text needs no further comparison; a non-exact match is aligned by structural anchor (structural_ref) first, with a lexical-similarity fallback when a structural anchor has moved or disappeared. Every alignment carries a confidence — 1.0 for an exact hash match, high for a structural-anchor match, lower and similarity-scaled for the positional fallback. When two or more passages hash-identically — repeated boilerplate is routine in regulatory drafting — the tie is broken by nearest structural or positional match: the candidate whose structural_ref is closest to the source passage's wins, and where structural refs tie too, the candidate closest in passage seq wins. The lexical-similarity fallback itself scores each candidate by token-level Jaccard similarity over the two passages' normalized text, and its search scope is bounded to the same or an adjacent structural section — never the whole document — so a short, generic phrase cannot align across two unrelated locations just because it reads the same. Diffing then runs a character-level diff over each aligned pair, producing typed changes — added, removed, modified — each with its own char offsets into the two versions' own stored text.

A low-confidence alignment does not proceed to a "modified" classification on a guess. It is flagged ambiguous and routed to escalation (§6) — the diff would rather say "I could not confidently match these two passages" than silently pick the nearest one and let a wrong pairing look like a real content change.

Alternatives considered

OptionRejected because
Whole-document diff (Myers over the full text)One pass, but the output doesn't map to the structural units — passages, obligations — the rest of the system reasons about, and a single reflow anywhere produces an unreadable diff everywhere.
Embedding-similarity change detectionFinds drift, not edits (ADR-004/ADR-008): it can say a passage moved semantically without saying which words changed, which is exactly the information a citation needs.
Ask the model to diff two full documentsUntestable against a known answer, and silently drops changes in long documents — the stated reason ADR-004 splits detection from interpretation in the first place.

Trade-off accepted, stated plainly (ADR-004). Deterministic alignment assumes the document's structure is stable enough to anchor on. Wholesale restructuring — renumbered sections, moved text — breaks this assumption for many passages at once, not one. This is not a rare edge case in regulatory drafting; a final order routinely renumbers a draft's sections. See §14.

3. Evidence-linked extraction

Design

Extraction is the one place the model reads source text and produces a structured claim — an obligation's text, category, deadline, applicability — and it runs only after deterministic diffing has already enumerated what changed (or, for a proceeding's first version, over the baseline text). The model is given the passage text with explicit offset markers and instructed to quote verbatim substrings for anything it asserts as fact, never to paraphrase into the citation field. Every claim field is one of two kinds, and the UI marks the difference: a cited field carries a citation object and must verify (§5) before it is shown as established; an inferred field (e.g., a category label the text doesn't use verbatim) carries no citation and is always shown as inference, never as fact.

An obligation with no citation on its load-bearing fields does not enter obligation state. It drops to the escalation queue as a candidate, same as a failed citation verification (§6) — the contract is symmetric: no evidence, no assertion, regardless of which stage produced the gap.

4. Company-context data model

Design

Three entities carry the company side of the join. Obligation — a regulatory duty the company holds, sourced from a proceeding or entered directly. Project — an internal initiative that fulfills or is constrained by obligations. Document — the company's own artifacts: filings, tariffs, compliance memos — written in the company's language, evidentiary rather than regulatory. Obligations relate to projects many-to-many (a project can discharge several obligations; an obligation can span several projects) and to documents by evidentiary link (a filing that discharges, or a memo that interprets, a specific obligation).

The synthetic corpus (data/, per the build board) is roughly 8 obligations, 3 projects, 4 documents, deliberately written in the company's own phrasing rather than the docket's — this is not incidental realism, it is the reason ADR-008 adds semantic retrieval on top of lexical: an obligation record that says "quarterly outage reporting" will not lexically match a docket clause that says "the utility shall submit reliability metrics no less than four times annually."

5. Citation verification (ADR-003)

This is the depth area. It is the hardest technical decision in the build and the one the product makes visible rather than buries (ADR-003; CLAUDE.md). Everything above exists to feed it evidence; everything below (§6–7) exists to handle what it refuses to verify.

Contract

A citation is (document_version_id, char_start, char_end, quoted_text). The verifier: (1) resolves document_version_id to the stored raw text and checks its SHA-256 against source_sha256 — this catches corruption of the stored copy itself, independent of anything about the citation; (2) slices text[char_start:char_end]; (3) normalizes both the slice and quoted_text through an explicit, tested pipeline; (4) compares. The comparison is exact string equality after normalization — never a similarity threshold. A paraphrase is exactly what an auditor will not accept (ADR-003), so "close enough" is not a verification outcome this system produces.

Normalization — stated explicitly, because an unstated normalization rule is a silent one

RuleWhat it handles
Whitespace collapseRuns of spaces/tabs/newlines → single space; leading/trailing trim. Handles PDF reflow and the model's own line-wrapped reproduction of a quote.
Unicode NFKCLigatures (ﬁ→fi), smart quotes → straight quotes, non-breaking space → space. Canonical target is NFKC; both source slice and quoted_text pass through it before comparison, never just one.
Dash variantsEm/en dash normalized to hyphen for comparison only — the display copy keeps the source's original character.
CaseNot normalized. A citation with wrong case is suspicious — it can mean a defined term was altered — and is treated as a genuine mismatch, not noise.
Hyphenation across line breaksResolved once, at ingestion extraction (§1), before offsets exist — never at verification time. Verification must not "fix" text out from under an offset it didn't compute.

Outcomes

OutcomeMeaningProduct behavior
verified_exactByte-identical after normalization, at the given offsets.Shown as fact; source span highlightable on click.
verified_normalizedMatches only after a specific rule fired.Shown as fact; which rule fired is recorded for audit, not shown as a caveat to the reader.
near_matchNot found at the given offsets, but found by a bounded local re-anchor search (see below).Downgraded confidence; surfaced as "offset auto-corrected" in the audit history — never silently accepted at face value.
unverifiedNo match at the offsets or within the search window.Never displayed as fact. Routed to escalation, labelled "unverified — quote does not match source," with a link to what the offsets actually contain so a reviewer can see the real passage.

Near-miss re-anchoring — a deliberate, bounded compromise

Offsets can be slightly wrong even when the quote is real: the model's own arithmetic on where a passage starts can be off by a few characters. Rather than reject every off-by-a-little citation outright, the verifier searches a bounded window (±N characters, N a tunable constant — not yet fixed; see open item below) around the given offsets for the normalized quoted_text as an exact substring. A hit inside the window is near_match, never silently promoted to verified_exact. A miss is unverified.

Trade-off, stated both directions. Too narrow a window rejects a true citation whose offset arithmetic drifted slightly — costs a review, which is the correct failure direction ("absence is denial"). Too wide a window risks confirming a coincidental identical phrase elsewhere in the document — a false accept, which is the one failure this design cannot tolerate. The window width has to be small enough that coincidental identical phrasing within it is implausible for the corpus's prose. The actual value has not been chosen against real data — it needs to be set from the eval corpus (§9), not from intuition, and is marked open rather than filled with a plausible-looking default.

Open — not yet decided. (1) The re-anchor window width N. (2) Whether near_match citations should ever be permitted to back a final-status comply action, or whether final-status actions should require verified_exact/verified_normalized only. Leaning toward the stricter rule for final, but this has not been tested against the corpus and should not be asserted as decided.

The harder case: a true substring that reverses meaning

A citation can pass exact-match verification and still misrepresent the source, if the model quotes a real, correctly-offset substring that omits an adjacent qualifier — dropping "shall not" to leave "shall," or quoting a clause without the "unless" three words later that governs it. Verification proves the text exists at that location; it does not by itself prove the text supports the claim. These are different guarantees and this design does not pretend otherwise.

Mitigation, stated as a heuristic guard rather than a solved problem: on any verified citation, a cheap adjacency check scans immediately outside the cited span for negation/qualifier words (not, shall not, except, unless, provided that). If one is found abutting the boundary, the citation is not auto-rejected but is downgraded to near_match-equivalent handling and flagged suspect_truncation for review — the span should have been widened to include it. This catches an adjacent qualifier. It does not catch a qualifier two sentences later, or one stated once and applied by reference to several following clauses. That gap is real, unclosed by this design, and is called out again in §14 rather than left to be discovered at the panel.

Offsets are scoped to a version, never projected across versions

A citation into version 1 stays a citation into version 1's immutable text. It is never re-projected onto version 2's text through the alignment computed in §2. The alternative — a document-level coordinate space every version maps into, so a citation could "follow" a passage across versions — was rejected because that mapping is the alignment problem, and alignment has its own confidence and its own failure mode (§14); routing citation correctness through it would let an alignment error silently corrupt a citation that was otherwise exactly right. The accepted cost: when a change record says "this obligation's deadline moved," the UI shows two citations — the old span in the old version, the new span in the new version — not one citation that claims to have moved. That is correct, and it is more UI surface than a single "moved" pointer would be.

Performance and placement

Verification is a bounded string slice and comparison — no model call — so it runs synchronously in the extraction/interpretation path and gates the write: a claim's citation must verify before the claim can be written to obligation, change-interpretation, or impact-mapping state. It does not need to re-run at read time, because document versions are append-only and never mutated after ingestion; the only case that forces re-verification is a change to the stored source itself, which the append-only invariant should make impossible outside of tested migrations.

Adversarial test discipline (T5, T17)

The verifier is tested against deliberately corrupted citations before anything is wired to it: a fabricated quote (words changed) must produce unverified; a truncated quote that drops a governing negation must produce suspect_truncation; an offset shifted by a few characters into real matching text must produce near_match, not a silent verified_exact. The passing bar for the corruption tests is 100% rejection, not "mostly." A single false accept defeats ADR-003's entire premise — there is no partial credit for a citation verifier, because the product's claim to the reader is "if it is shown as fact, it verified," not "it usually verified."

6. Confidence & escalation (ADR-006)

Design

Confidence is attached at every stage that makes a judgement, and each source is kept distinct rather than collapsed into one number: alignment confidence (§2, rule-derived — exact hash, structural-anchor, or lexical-fallback), citation verification outcome (§5, a gate, not a score — unverified always forces escalation regardless of any other signal), and model-reported confidence on interpretation and impact-mapping fields.

Model self-reported confidence is treated as an ordinal signal (low / medium / high), not a probability. Raw confidence numbers from language models are known to be poorly calibrated, and trusting a number like 0.83 at face value would be fake precision dressed as rigor. The escalation threshold is set and tuned against the eval set's known answers (§9) — against outcomes, not against the model's own stated certainty.

Below threshold, a result does not enter obligation, change, or impact-mapping state at all. It becomes an escalation record: what was attempted, why it stopped short, and a link to the source and the review action needed. The threshold itself lives in configuration (CONFIDENCE_THRESHOLD), not as a constant in code — per ADR-006, so it can move as the eval evidence accumulates without a redeploy of logic.

Open — not yet tuned (decision-log open item 2). The starting default is deliberately conservative: escalate anything below ordinal high. This is a defensible prior, not a measured setting — it has not been checked against precision/recall numbers because those numbers do not exist yet (§9). It should move once they do, and this document should be updated when it does, not silently left stale.

Trade-off accepted (ADR-006). A review queue nobody empties is its own failure — the review surface has to be fast enough that clearing it is routine. That is a product requirement on the reviewer view (§7), not just an engineering one, and is why the escalation record carries enough context (source link, reason, prior confidence) to be actioned in one look rather than requiring the reviewer to re-derive it.

7. Reviewer routing

Design

Routing follows the draft/final split (ADR-005) with no shared code path. A change on a draft version produces a monitor-or-comment action, owned by the regulatory affairs analyst (ADR-001's one persona), with an option to flag for a comment-filing review. A change on a final version produces a comply action carrying an effective date, routed to the analyst and to the obligation's owner — a named person recorded on the obligation record itself, not inherited from the project. (Routing to a project owner was the earlier wording; it was wrong, because one project carries obligations that different people answer for.) The role a claim routes to is a field on the action record, not inferred from who is looking at the screen.

The build board's cut list allows dropping the multi-role reviewer model under time pressure in favor of a single reviewer role. This design accommodates that gracefully: routing degrades to "everything to the analyst" by changing one lookup, not by branching logic, because the analyst is the primary owner in every case already — the project-owner routing on final actions is additive, not load-bearing.

8. Audit history & rollback

Decision: event-fold, not snapshots

This was an open question in the decision log (item 3). The choice made here is event-fold: every state-changing action appends an immutable event; current state in every table is the fold of its events; rollback is a new event that restores a prior fold point, never a destructive edit of history.

Why, against the alternative

Event-fold (chosen)Snapshots
Extra workNone — the audit-trail requirement (best-practices §11) already means every transition is logged; storing that log as the source of truth instead of as ephemeral lines is the same work, kept.A full state copy per transition, which duplicates the growing project state repeatedly.
What rollback explainsActor, reason, and the source change behind every transition — this domain needs "why did the obligation status change on this date," not just the before/after blob.What the state was, not why it changed — coarser, and wrong for a compliance audit trail.
Cost at this scaleFolding is cheap over ~8 obligations and one proceeding. It is not free at arbitrary scale — see below.Read is O(1) regardless of history length — the argument in snapshots' favor, and it does not apply yet.

Trade-off accepted, stated plainly. Event-fold requires that current-state tables are never written outside the event-apply path — a direct UPDATE against, say, obligation.status from anywhere else makes state and history diverge silently, which is exactly the failure best-practices §26/§27 describe: a derived value that is wrong but announces nothing. The design forbids this by convention now and should enforce it structurally (only the event-apply function issues writes to state tables) before it is trusted with real data. Folding also does not stay cheap forever — at a scale this MVP does not reach, folding the full event stream on every read becomes the bottleneck, and the standard answer (periodic snapshot + fold-forward from the snapshot) is a later addition, not a redesign, because it composes with an event log and would not with snapshots alone.

Per the cut list, rollback (the restore action) can be dropped before audit history is; this decision supports that directly — the append-only log is kept unconditionally, and "restore to a prior point" is a thin UI action over a read path (fold-and-diff against current) that already has to exist for the audit view itself.

10. Data isolation

Every company-scoped table carries company_id from the start, even though the 48-hour build has exactly one synthetic company. Queries go through a repository layer that injects company_id from the resolved principal, not from client input, through one chokepoint (best-practices §3/§16) rather than a per-handler check that drifts. A negative test — company A's principal cannot read company B's proceeding or obligation even given a guessable ID — is task T8 on the build board. Until T8 lands, isolation is a design property and not a demonstrated one, and this document should not be read as claiming otherwise. Retrofitting isolation after the schema exists is the mistake best-practices §16 documents; building the query layer as if a second tenant existed, while only one does, is cheap now and expensive later.

Proceedings themselves are not company-scoped — a docket is external and can be tracked by more than one company context — while obligations, projects, and documents are. This split matters for isolation: a citation into a proceeding's document version is safe to share in principle, but the obligation record that references it is not, and the isolation boundary sits on the company-owned tables, not on the shared regulatory text.

11. Security

SQLite as a local file with no exposed network service beyond the FastAPI app itself (ADR-007). Model API keys come from environment configuration, never committed or logged. Real authentication (login, session management) is out of scope for the reviewer-run prototype and is stated here as a known gap, not a silent one — the code should not carry an implicit "no auth needed" assumption that would ship unnoticed past this build. In a real deployment, company-context documents are confidential regulated-industry filings, which means encryption at rest and access logging are productionization requirements; ADR-007 already commits to saying what changes past this prototype's scale, and this is one of those things — explicitly deferred, not implicitly forgotten.

13. Request path — main workflow

From a new version landing to an analyst seeing a routed action.

  1. Ingest. New document_version arrives (upload or corpus script). Extract text, compute source_sha256, store immutably. Segment into passage rows with stable offsets (§1).
  2. Diff. Align this version's passages against the proceeding's prior latest version; produce change rows with change_type and alignment_confidence (§2). Low-confidence alignments create an escalation row immediately and the change stays pending.
  3. Branch on status. document_version.status (draft/final) selects the downstream action vocabulary now, not later — the draft and final paths never merge (ADR-005).
  4. Interpret. For changes above the alignment threshold, a scoped model call reads the from/to passage text and classifies materiality, producing citations for any assertion beyond the raw diff (e.g., "the deadline moved from X to Y").
  5. Verify. Every citation produced in step 4 runs through the verifier (§5) before it can attach to the change record. unverified routes to escalation; the change's materiality is not written as settled until its citations are.
  6. Map impact. For changes marked material, retrieve candidate obligations/projects/documents — lexical (BM25) first pass, semantic re-rank for obligation matching (ADR-008) since obligations are worded in the company's own language. The model confirms or rejects candidates with confidence; any asserted linkage text is again citation-gated.
  7. Gate on confidence. Impact mappings and extractions below threshold (§6) do not reach confirmed — they sit as pending_review and generate an escalation row.
  8. Recommend and route. Confirmed, above-threshold mappings generate an action: monitor/comment for draft, comply-plus-effective-date for final, with a recommended reviewer role (§7).
  9. Record. Every write in steps 1–8 appends an event; the state tables are that log's fold (§8), never written to directly.
  10. Surface. The analyst workspace reads current state directly (the fold already happened at write time, not at read time). Clicking a claim highlights its exact verified source span; unverified items sit in the escalation/review queue with the reason shown, not hidden behind a generic error.
  11. Review. A reviewer approves, rejects, or amends an escalated item; that action is itself an event, which updates state and can re-trigger routing.

14. Failure modes

Where this design is honest about what it does not solve. Evaluation dimension 1 asks where modern AI fails and how the system was designed around it — not whether it was designed to never fail. Each item below states the failure, the blast radius, and the actual mitigation, including where the mitigation is partial.

Retrieval misses (impact mapping, ADR-008)

A missed lexical/semantic match means a real change is not linked to the obligation it affects. This degrades explanation quality, not change coverage — the deterministic diff (§2) already enumerated the change independent of retrieval, so a missed link surfaces as a visible, unmapped item in the analyst's queue ("change detected — no automatic obligation match"), not as a change that silently vanished. This separation between "did something change" (complete, deterministic) and "what does it touch" (lossy, retrieval-based) is the load-bearing design choice ADR-008 makes, and it is why a retrieval failure is recoverable by a human glance rather than invisible.

Retrieval service failure, as distinct from a retrieval miss

A retrieval miss (above) is the lexical or semantic step running and returning the wrong or no candidate. This is a different failure: the service cannot run at all — a timeout, a dead embedding provider, a corrupt index. The chosen behavior: escalate to review, not degrade to lexical-only. A silent fall to lexical-only would return a plausible-looking impact mapping under a failure condition the analyst has no way to see — the exact shape of failure best-practices §26/§27 name, and the one ADR-006 exists to close off. An outage the analyst can see and act on is worth more than a partial result that looks the same as a working one. The accepted cost: a retrieval outage stops impact-mapping for affected changes rather than degrading gracefully underneath them. That cost is accepted because a hidden degrade is worse than a visible stop.

Tables

The challenge brief asks about tables directly, and nothing elsewhere in this document does. A table flattened to text loses its row structure — a cell's meaning depends on the header above it, and flattening drops that link, so a citation that lands on a bare cell offset is not gradable without the header that gives it context. Segmentation compounds this: a single inserted or deleted row shifts every offset after it, and a diff run over the flattened text can present a whole table as changed when only one row moved. The intended fix is to segment a table as its own passage type — row tied to header, as the citation unit — so a cell's offsets carry its header by construction and one row's insertion does not misalign the rows around it. This is not built. Tables in the current pipeline are ordinary text and inherit every problem above.

Footnotes

The segmentation model (§1) has no passage type for a footnote and no anchor tying one back to the clause it qualifies — a footnote is ingested as ordinary body text wherever it falls in reading order, disconnected from the clause above it. This matters because a footnote in regulatory drafting often carries the exception that changes the obligation: the clause reads as absolute and the footnote is where "unless" lives. Losing the link means an obligation can be extracted as unqualified when the source qualifies it a few lines down. Not built.

The model misquotes or misreads

Fabrication and shifted offsets are caught by the verifier (§5) at a 100% bar on the corruption test suite. The residual, unclosed risk is the truncation case: a real, correctly-offset substring that drops a distant qualifier. The adjacency heuristic catches a qualifier touching the cited boundary; it does not catch one two sentences away or one governing several clauses by reference. The distinction that matters: citation verification proves a quote exists at a location. It does not prove the interpretation drawn from that quote is correct. Those are different guarantees, and conflating them would be the single easiest way for this design to overstate what it delivers.

Wrong-occurrence citations

This is the subtle one, and it deserves the prominence the two cases above don't need. Regulatory documents repeat boilerplate — the same clause, the same defined term, the same standard phrase, at several points in one document. A citation carries exact offsets, and the verifier (§5) checks that the quoted text matches the text at those offsets. That check passes regardless of which occurrence the model was actually reasoning about. If the model reads occurrence B of a phrase but cites the offsets of occurrence A, the citation is real, the offsets are real, the quote matches — and the claim built on it can still be wrong. Verification reports green, and green is the wrong answer. This is distinct from the truncation case above: nothing about the cited span itself is malformed, so the adjacency heuristic does not catch it. Mitigation direction, not implemented. Three shapes, in rough order of cost: a surrounding-context window check, comparing text around the cited offsets against the passage the model was actually shown, not just the quoted substring; a structural-path check, comparing the citation's structural_ref against the passage the model was given, independent of text content; or a uniqueness check at extraction time, flagging any quoted phrase that recurs elsewhere in the document so the model is forced to disambiguate before the claim is written. None of these is built. The gap is real and unclosed.

At 10x latency

The only latency-sensitive stage is model calls (interpretation, extraction, impact confirmation). Ingestion, segmentation, and diffing have no model dependency and are unaffected at any multiple — a proceeding's changes are always enumerated even if interpretation stalls completely. Model-dependent stages are intended to run as background work (best-practices §9) so a request returns "N changes detected, interpreting" rather than hanging; a bounded per-call timeout and retry (best-practices §8) stop one slow call from stalling a whole batch. A call that ultimately times out leaves that item as "needs interpretation" in the workspace — visible, not dropped. Open scoping question: whether this ships as a real background job or a simpler request-time timeout with a "try again" surface depends on what the 48 hours allow; either is acceptable as long as the failure stays visible rather than silent (best-practices §26) — a hang with no explanation is not.

When the model is simply wrong

Not a hallucination, not a bad citation — the model reads a verified passage correctly and reaches a materiality judgement a domain expert would disagree with. This is precisely the case ADR-006's confidence and escalation exist for, and the honest limit is that confidence is an imperfect proxy for correctness: a model can be wrong while reporting itself confident. The mitigation stack, stated as partial: ordinal calibration against eval outcomes rather than trusting a raw score (§6); draft-versus-final removed from model judgement entirely (ADR-005), closing off one whole class of wrong guess; and human review sitting between any impact mapping and an action with a deadline attached.

What is not solved, stated plainly. There is no mechanism that samples the model's confident calls — the ones that never reach the escalation queue because the model itself did not flag them — and checks them against ground truth. The escalation queue only catches what the model flagged as uncertain about itself; it cannot catch what the model was confidently wrong about. At production scale this needs sampled human audit of confirmed, non-escalated output, not just of the queue. This is the single largest unresolved risk in the design, and it is unresolved because closing it requires exactly the real-user, real-volume evidence this 48-hour build does not have — not because it was overlooked.
