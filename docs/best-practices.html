Best-Practices Architecture

Guidelines, design patterns, and hard-won lessons worth adopting on most new software projects — established practice, hardened by real production fixes. Hand this to a new project so it starts smarter. Each entry: the "why", concrete do/avoid, and external references. Nothing here is specific to one application.

Started 2026-07-26 · living document. Maintenance: at each commit, ask "did this teach a general principle a new project should follow?" Fold it in selectively — keep entries general and portable, push project-specifics to decisions.html, and prune bloat. A playbook people re-read beats an exhaustive one they don't.

How to use. These are strong defaults, not laws — adopt the reasoning, adapt the specifics to your context and scale. Bootstrapping a project? Start with §1 (start simple), §12 (tests), and §9/§10 (deploy & ops); layer the rest in as you touch each area. Over-applying any of these (premature abstraction, gold-plated infra) is its own anti-pattern.

Architecture

1Start simple; earn complexity

Most projects die of complexity they added before they needed it. A well-structured modular monolith ships faster, is easier to reason about, and can be split later along seams you've actually discovered. Distribute (microservices, queues, caches, sharding) only when a real constraint forces it.

Do

  • Begin with one deployable, internally modular by domain; extract services when scale/ownership demands it.
  • Apply YAGNI / KISS: build what the current requirement needs, no speculative generality.

Avoid

  • Microservices, event-sourcing, or a cache before you have the load or the team to justify them.

Refs: Fowler — MonolithFirst · Fowler — YAGNI · Shopify — Modular Monolith

2Clear boundaries & dependency direction

Coupling is what makes software hard to change. Keep the core domain independent of frameworks, databases, and I/O; let dependencies point inward (ports & adapters / hexagonal / clean architecture). You can then swap a UI, DB, or vendor without touching business logic, and test the core in isolation.

Do

  • Separate domain logic from delivery (HTTP), persistence, and external services behind small interfaces.
  • Make the direction of dependency explicit; the domain imports nothing framework-specific.
  • Isolate each external system behind an anti-corruption layer — an adapter that maps it to one canonical internal record (a source tag marks origin). Adding the Nth provider becomes a pure adapter change; dashboards, analytics, and AI context keep working unchanged and vendor quirks don't ripple inward.

Avoid

  • Business rules tangled into controllers, ORMs, or vendor SDKs.

Seen in peers: vitalnexa normalizes every wearable (Oura/WHOOP/Dexcom) into one test_results shape; citelocal wraps every data provider behind one interface — a new provider is one adapter fn.

Refs: Cockburn — Hexagonal · Martin — Clean Architecture · Fowler — PDD layering

3One chokepoint per cross-cutting concern

Cross-cutting logic — auth, redaction, rate-limiting, formatting, per-item controls — duplicated across call sites drifts out of sync and re-introduces bugs you already fixed. One place to change is one place to get right and to test.

Do

  • Route each cross-cutting concern through a single function/middleware/layer applied uniformly.
  • Compose small, single-responsibility units (e.g. an orchestrator delegating to specialists with clear contracts).

Avoid

  • Copy-pasted policy logic in N handlers.

Refs: SRP · Fowler — Patterns of Enterprise App Architecture

Data & contracts

4Model data deliberately; migrate safely

The schema outlives most code and is the hardest thing to change under load. Model it on purpose; evolve it with versioned, ordered migrations that are safe to run on live data.

Do

  • Schema in version-controlled migrations; forward-only and additive where possible (expand → migrate → contract).
  • Index for real query patterns; enforce invariants with constraints, not just app code.
  • Native enums need an explicit add-value migration; large tables need online/backfill-safe changes.
  • Track provenance on derived facts — a source field with precedence (human-authoritative > external feed) so a re-sync can't clobber a human edit.

Avoid

  • Hand-run or destructive migrations; a rename/drop in the same release that still reads the old shape.
  • Init-only migration scripts that skip existing databases (e.g. docker-entrypoint-initdb.d, which runs only on an empty volume), or two schema paths (auto-create_all + migrations) that silently drift. Make a migration runner with an applied-ledger the sole authority.

Refs: Kleppmann — DDIA · Fowler — Evolutionary Database Design

5Idempotent, natural-keyed writes; best-effort side-effects

Syncs, imports, and retries happen. A write keyed by a natural key that UPSERTs converges on replay instead of duplicating. And a secondary effect (analytics, enrichment, memory) must never roll back the primary transaction.

Do

  • UPSERT on a natural key (entity + date), not blind insert; use idempotency keys for external calls.
  • Guard best-effort side-effects so failure degrades to a no-op; use a savepoint so a sub-step failure rolls back only itself.
  • Claim before dispatch for concurrent fan-out: mark work claimed (e.g. last_sync = NOW()) in the same transaction that selects it, before launching parallel fetches — gives at-most-once behavior across concurrent triggers (tabs, devices) without standing up a queue.

Avoid

  • A best-effort enrichment that can abort the user's actual save.

Refs: Stripe — Idempotency · Kleppmann — DDIA

Hardened here: lab ingestion behind a savepoint on upload; upserts keyed by (principal, biomarker, date).

6Explicit, versioned contracts

Every interface between components (HTTP API, event, library) is a promise. Make it explicit and evolve it without breaking callers, so teams and clients move independently.

Do

  • Define request/response schemas; validate at the boundary; return consistent error shapes and status codes.
  • Version deliberately; keep backward compatibility (additive changes); deprecate on a timeline, not abruptly.

Avoid

  • Silent breaking changes; leaking internal models straight onto the wire.

Refs: Stripe — API versioning · SemVer

7Verify external data before trusting it

A shallow "success" is not validity — HTTP 200 doesn't mean a page is what you think (expired postings, generic landing pages, JS shells all return 200). Trusting the shallow signal surfaces stale/wrong data to users.

Do

  • Verify content and dates: does it actually contain the expected entity? Is it in-date? A specific record vs a landing page?
  • Treat "can't confirm" as unverified, distinct from "confirmed good".

Avoid

  • Equating reachability with correctness or freshness.

Learned here: expired job postings that all returned 200; fixed with content-marker + expiry + entity-on-page checks.

Reliability & operations

8Design for failure

Networks, dependencies, and disks fail; the question is whether your system fails well. Bound every remote call, retry transient errors safely, and degrade gracefully instead of cascading.

Do

  • Set timeouts on every I/O call; retry only idempotent ops, with exponential backoff + jitter and a cap.
  • Degrade gracefully — a failing non-critical dependency returns empty/cached, not a 500.
  • Use circuit breakers / bulkheads when a dependency can overwhelm you.
  • Wrap each paid/external API in one resilient client (timeout + backoff + rate-limit + cache, with an injectable clock/cache so tests never touch the network) rather than scattered try/excepts; refresh OAuth tokens from day one — a 401 that silently returns empty makes an integration die quietly.

Avoid

  • Unbounded waits; blind infinite retries (retry storms); one slow dependency taking the whole request down.

Refs: AWS — Timeouts, retries, backoff w/ jitter · Nygard — Release It!

9Slow work belongs in the background

Anything that can exceed a request budget (proxies typically cut at ~60s) must not run synchronously in the request. Serve the last stored result instantly and refresh asynchronously.

Do

  • Persist results; the endpoint returns the stored copy at once with a "refreshing" flag; poll for the new one.
  • Run refresh via a managed background mechanism (framework tasks or a real job/queue) — not a raw thread the server may reap; de-dupe in-flight work per key.
  • For wall-clock-local schedules, run the cron often in UTC and gate on a stored local-time target — immune to daylight-saving shifts, unlike a hand-computed UTC hour.
  • Fan out independent work instead of a straight line. When a batch job does the same independent unit N times (one digest per user, one check per URL), run them on a bounded pool through one small parallel_map-style primitive that returns results in input order and captures a per-item failure in its slot (so one unit's error never sinks the batch). Give each worker its own DB session — sessions aren't thread-safe — and keep a kill switch (width 1 → sequential) to revert by config.

Avoid

  • Synchronous calls that outlive the gateway timeout; fire-and-forget threads under a worker that recycles.

Refs: 12-Factor (VIII, IX) · Google SRE Book

Learned here: a ~2.5-min search timed out synchronously; a raw background thread died under a cycling deploy — moved to stored-result + managed refresh.

10Deploy & migrate safely

Deploys that skip the safety net or run migrations by hand break in production; rapid successive deploys recycle instances and kill in-flight work; assuming a deploy "went out" is how stale code lingers.

Do

  • Gate merges on the regression net; run migrations automatically on release.
  • Verify the deploy landed (running build/commit), not just that you triggered it; keep releases small and reversible.
  • Measure real deploy downtime with a probe (a 1 s loop over /health) before you try to optimize it — and verify recovery by probing the service, not the deploy tool's status, which can lag real recovery by minutes. Design the client to degrade gracefully during the window (timeouts, honest retry) rather than chasing true zero-downtime first.

Avoid

  • Hand-run migrations; assuming a queued deploy succeeded; a storm of successive deploys.

Refs: 12-Factor (V) · Fowler — Blue-Green

11Observability; diagnose from evidence

You can't fix what you can't see, and guessing wastes time and "fixes" the wrong thing. Emit signals, keep an audit trail, and diagnose by reading real state before theorizing.

Do

  • Structured logs, metrics, and traces; log significant state changes to an audit trail.
  • When something's wrong, inspect the actual data/logs first; confirm root cause before fixing.

Avoid

  • Guessing at a cause and patching a symptom that wasn't the problem.

Refs: Google SRE Book · OpenTelemetry primer

Learned here: "why reconnect Oura?" — answered from DB + audit log (no connection row, no connect event), not assumption.

Quality & craft

12Tests & evals are the safety net

A frozen set of cases run on every change tells you whether the system improved or quietly broke; most outages are re-breaks of something once fixed. For non-deterministic (AI) systems, split the net: deterministic checks in CI, judged checks on demand.

Do

  • Maintain a golden/regression suite gated in CI; follow the test pyramid (many fast unit tests, fewer integration/E2E).
  • Every bug fix ships a guard — the cheapest test that would have caught it. Extract a pure helper to make a behavior testable.
  • For open-ended AI output, use LLM-as-judge against a rubric (opt-in; replay real past failures in it); score dimensions separately.
  • Tests run offline by default: neutralize spend/prod secrets before test collection (an import-time side effect can bill you or leak live keys) and default to a mock provider.
  • Run the whole suite before shipping — not just the tests you believe are affected. Your model of the blast radius is exactly the thing that is wrong when you break something.
  • When a change makes an old test fail, decide deliberately: is this a regression (fix the code) or a superseded contract (update the test, and write down why)? Silently flipping an assertion to green is how a real defect ships.

Avoid

  • One quality number hiding which dimension regressed; only-manual "it works" checks.

Refs: Fowler — Test Pyramid · Fowler — CI · OpenAI Evals · Promptfoo

13Fix the class, not the symptom

Patching the one reported line leaves the same failure lurking on paths you didn't look at and invites a re-break. Fixing the class + a guard is what makes a system get monotonically better.

Do

  • Trace the failure to its class — every producer and consumer of the bad state, forward and backward — fix the general cause, then add the guard (§12).
  • Beware the per-vendor patch: fixing the one provider that was reported leaves every sibling broken. If the rule is "exclude index pages", express it structurally, not as a list of that vendor's URLs.
  • When matching text, match the field you actually mean (path, not the whole URL; a title, not the whole document). Over-broad matching passes your examples and misfires on real input.

Avoid

  • The one-line patch that only silences the reported instance.

Learned here: an email listing's description orphaning — the cause was two independently-keyed lines, not the one row reported.

14Readable code, small changes, real review

Code is read far more than written; clarity is a feature. Small, reviewed changes are easier to reason about, test, and revert, and reviews spread knowledge and catch what tests can't.

Do

  • Match the surrounding style; name for intent; small functions; comments explain why, not what.
  • Small, focused commits with meaningful messages; review every change (correctness, clarity, security).

Avoid

  • Giant mixed-concern PRs; clever code that only the author can read; DRY taken to premature abstraction.

Refs: Google — Code Review · Fowler — naming/cache-invalidation

15Measure before you optimize

Intuition about performance is usually wrong; optimize the measured hot path, not a guess. The common real wins are algorithmic and I/O-shaped, not micro-tweaks.

Do

  • Profile / measure first; set latency & cost budgets; fix the biggest offender.
  • Kill N+1 queries (batch/eager-load); cache with a clear invalidation strategy and TTLs.

Avoid

  • Premature micro-optimization; caches without an invalidation plan (stale-data bugs).

Refs: Knuth — premature optimization · Use The Index, Luke

Security & supply chain

16Security & confidentiality by construction

Authorization scattered across handlers drifts and leaks. A single resolution chokepoint, least privilege, and context-aware visibility keep the confidential surface small and auditable. Secrets and personal data must never live in code or logs.

Do

  • Resolve authorization through one chokepoint; deny by default; fail closed; row-scope multi-tenant data by tenant id on every query.
  • Make visibility context-aware where needed (who is viewing and whose data, in what context).
  • Keep secrets in env/secret stores; encrypt tokens & PII at rest (envelope encryption with rotatable keys lets you re-key with zero downtime); validate and encode all input/output.
  • Fail closed at startup — refuse to boot in prod with a default/weak secret or unconfigured encryption.
  • Gate locked/paid content by server-side omission — never ship a payload the client is trusted to hide; read entitlements/authz from the server or DB, never from the token.
  • Test the negative — prove tenant/user A cannot read B's data. A control you've never attacked adversarially is an assumption, not a guarantee.

Avoid

  • Per-handler ad-hoc auth; secrets in code/config/logs; trusting client input.
  • Leaning on regex denylists as the primary guard for injection/PII — brittle and bypassable; make them one layer behind a fail-closed validator.

Refs: OWASP Top Ten · OWASP ASVS · 12-Factor — Config

17Minimize & vet dependencies

Every dependency is code you didn't write but now own — a surface for bugs, breakage, and supply-chain attacks. Prefer borrowing a pattern over adding a library; when you do add one, pin and vet it.

Do

  • Weigh each dependency (maintenance, size, blast radius); prefer the platform/stdlib when it suffices.
  • Pin versions with a lockfile; scan for known vulns; keep deps current.

Avoid

  • A framework to save ten lines; unpinned deps; blindly trusting transitive packages.

Refs: OWASP Dependency-Check · SLSA (supply-chain)

Applied here: kept the existing test harness rather than adding an eval framework — "borrow patterns, not dependencies."

18Collect less; expire & delete

Data you don't hold can't leak or be misused. Minimize collection, define a lifecycle, and make deletion real — both good practice and, increasingly, the law.

Do

  • Collect only what a feature needs; set retention/TTLs; support deletion end-to-end.
  • Separate confidential lanes (health/financial) with stricter access and logging.

Avoid

  • "Collect everything just in case"; data with no expiry or delete path.

Refs: GDPR Art. 5 — minimization · Privacy by Design

AI systems

19Ground on the system of record; never assert the unverified

The worst AI failure is confident and wrong — it happens when the model reads stale/partial state and insists on it. The fix is architectural: get inputs into the system of record, ground the model on that latest state, and have it reconcile discrepancies rather than defend what it can't verify.

Do

  • Ingest user inputs (uploads, forms) into the structured record the model reads — don't leave them as stranded blobs.
  • Prefer LLM structured extraction for messy inputs (OCR, varied PDFs) over brittle regex — constrained to the source, forbidding fabrication.
  • Make the model reconcile and flag conflicting sources; scrub PII before it reaches a model (independent validate → fail closed → only then call); keep confidential lanes confidential.
  • Separate VERIFIED facts from HYPOTHESIS in the model's context and pass provenance, so it cites what's known and flags what to check instead of asserting inferences as fact. Render the same catalog/rules the product persists, so the model's advice can't drift from the app.

Avoid

  • Answering from a stale cache while a fresher input sits un-ingested; trusting extraction without validation.

Refs: Anthropic — Effective agents · Prompt engineering · RAG

Learned here: a reply that defended a stale lab value over the user's uploaded one — fixed by ingesting the upload and guarding with a grounding judge.

20Budget cost & latency for models

Model calls cost real money and add real latency; unbudgeted, they surprise you in the bill and the p99. Treat tokens and time as first-class budgets.

Do

  • Right-size the model to the task (tier: a stronger model for interactive advice, a cheaper one for bulk); cache/dedupe calls; make expensive passes (large evals, deep research) opt-in; use batch APIs for non-interactive work.
  • Prompt-cache layout: freeze a byte-stable prefix with cache_control and put ALL per-request/volatile context in a separate later block — one stray timestamp in the cached prefix zeroes your hit rate.
  • Set token/latency budgets; run heavy work in the background (§9). Encode unit economics as authoritative config (prices in minor units, per-call cost, a per-tier usage cap the metering layer enforces) so margin is a code-level invariant, not a spreadsheet.

Avoid

  • The biggest model for every call; re-running identical prompts; slow model work in the request path.

Refs: Anthropic — Prompt caching · Message Batches

21Context is a budget: curate it, don't dump it

Everything you put in front of a model is paid for on every call, and noise crowds out signal. The failure is rarely a missing fact — it is a wall of state the model must wade through. Treat the context window like a budget with line items you can name.

Do

  • Measure before trimming. Print the byte/token size of each block you assemble per call; the distribution is usually lopsided and the biggest item is often a surprise.
  • Never interpolate a raw state object (a JSON blob, a settings dict, a cache) into a prompt. Render a curated subset and cap each value — blobs grow silently as unrelated features add keys.
  • Progressive disclosure: pass lightweight identifiers and fetch detail on demand, rather than pre-loading every domain into every call.
  • Keep an explicit boundary between facts the model needs now and state another surface owns.

Avoid

  • Pre-loading all domains "just in case"; letting an operational cache ride along as context because it happens to live on the same record.

Refs: Anthropic — Effective context engineering

Learned here: a per-turn context of ~2,400 tokens was 57% one block — and most of that was a raw settings dump carrying ~3,000 chars of an unrelated agent's cached output.

22Change prompts by experiment, not by faith

Prompts are load-bearing code with no compiler. As models improve, older prompts accumulate scaffolding they no longer need — but some of that verbosity is a learned correction that encodes a bug you already paid for. You cannot tell the two apart by reading. Measure.

Do

  • A/B it: same scenarios through old and new prompt, judged against a per-scenario rubric on the dimensions a change could plausibly break.
  • Repeat trials on anything safety- or policy-critical — a rare failure matters more than an average score. Single runs hide flakiness.
  • Distinguish what the model can infer (style, obvious behaviour — cut it) from what it cannot (domain policy, legal posture, corrections learned from real incidents — keep, and comment WHY so the next person doesn't re-cut it).
  • Pin the load-bearing clauses with a test, and keep the harness so the next trim must re-measure.

Avoid

  • Trusting a run where everything passes — a suite with no failures has no discriminating power; make the cases harder until it can tell the variants apart.
  • Comparing runs by which case-names failed instead of pass counts — a 2/3→0/3 collapse reads as "no new failures".

Learned here: a 42% prompt cut looked clean at 8/8 vs 8/8; repeat trials then caught it reintroducing a bug fixed months earlier, and the harness's own verdict logic was wrong in the same direction.

Product & knowledge

23Safe defaults; honest, accessible UI

Good defaults prevent whole categories of mistakes; reversibility turns a scary action into a safe one; and a UI should degrade honestly and work for everyone.

Do

  • Default to the safe choice; prefer hide + restore over hard delete; a single click shouldn't be irreversible.
  • Responsive/progressive UI (keep essential content visible at any width); honest, specific error & empty states.
  • Meet accessibility basics (semantics, contrast, keyboard, focus) and respect theme/motion preferences.

Avoid

  • Destructive defaults; one-click-permanent deletes; a layout that clips its key content on a narrow screen.

Refs: Nielsen — Heuristics · WCAG

24Config, environments & feature flags

Config in code can't vary per environment and leaks secrets; risky changes shipped all-at-once are hard to unwind. Externalize config and decouple deploy from release.

Do

  • Config from the environment; keep dev/stage/prod at parity; one build promoted across envs.
  • Use feature flags to ship dark, roll out gradually, and kill instantly; prefer trunk-based development with small merges.

Avoid

  • Hardcoded per-env values; long-lived divergent branches; big-bang releases with no off switch.

Refs: 12-Factor — Config · Fowler — Feature Toggles · Trunk-Based Development

25Living docs & structured memory

Decisions and durable knowledge that aren't derivable from the code get lost. A small, curated set of living docs pays for itself every time someone (or an agent) needs the "why".

Do

  • Keep an ADR log — one entry per real decision, capturing Options Considered + Consequences (and the bug that forced it, for incident-driven ones) — plus a structured-memory folder (here, .ai/) and a README that gets someone running fast.
  • Update this playbook at commit time, selectively — only genuinely general lessons.

Avoid

  • Docs that duplicate the code, or grow into an unread dump.
  • Contradictory or stale entries — mark superseded decisions and reconcile reversals; an unmaintained log actively misleads (a peer's still read "bcrypt" long after it moved to Argon2id, and documented a CI gate that didn't exist).

Refs: ADRs · Fowler — ADR

Degradation & data migrations

26A fallback must announce itself

A good fallback keeps the system up. A silent one keeps the system up while quietly changing what it means — and because nothing throws, nobody looks. The dangerous shape is a fallback that returns a value of the right type and shape but not the right quality: a vector of the right width carrying no meaning, a cached answer standing in for a live one, a stub that returns success. These survive for months because every check downstream passes.

Do

  • Make routing and reporting agree. If a health check or diagnostic names a provider, that name must come from what the code will actually execute, not from what is configured. Resolve to the effective mode — and let a stubbed or failed path report the fallback it really uses.
  • Treat placeholder config as absent. CHANGE_ME, TODO, your-key-here are truthy strings; a bare if key: reads them as configured. Normalize them to empty at the edge.
  • Never let an ambient credential re-route a subsystem. A key present for one feature must not silently select a provider for another — require an explicit opt-in, so the blast radius of adding a secret is what you intended.
  • Classify errors by whether retrying can fix them — and be humble about the boundary. Config rollouts propagate unevenly, so "unauthorized" can be transient. Retry, then conclude; a permanent latch on the first bad response is its own outage.
  • When a degraded mode is entered, log at error, expire the decision, and expose it to callers who can compensate (drop a weight, skip a term) rather than scoring noise.

Avoid

  • "Best-effort" wrappers that swallow the reason; reporting intent as if it were behaviour; inferring success from "no exception was raised".

Learned here: a stubbed HTTP client plus VOYAGE_API_KEY=CHANGE_ME made the platform report the voyage provider for months while every vector was a hash — and 55% of the ranking score was cosine over those hashes.

27A derived corpus migrates all at once, or not at all

Embeddings, hashes, encodings, tokenized indexes — derived data is only comparable within the scheme that produced it. Half-migrated, the system does not fail: it answers every query, plausibly, and wrongly. That is strictly worse than not migrating, because there is no error to notice and the old behaviour is gone.

Do

  • Enumerate every column, then ask which are read. A stale vector nothing compares is inert; one behind a similarity call is corruption. Write the coverage check as a test so the next migration cannot quietly skip a table.
  • Rebuild derived text with the app's own builders, imported — not a copy in the migration script. Two definitions drift, and the drift shows up as subtly worse retrieval nobody can date.
  • Re-assert the mode on every batch. A long migration outlives the conditions it started in; if the underlying provider changes, abort with a resumable message rather than finishing in two schemes.
  • Identify derived state that cannot be recomputed (anything learned rather than derived from stored text) and decide explicitly: reset to a neutral start, or keep and accept it's meaningless. Do not let it ride along by default.
  • Prefer a provider/model that can emit the existing dimension — it turns a schema migration into a data one.

Avoid

  • Backfilling only rows with NULL when the whole space changed; clearing learned state before the rebuild has actually finished; trusting a "success" exit that never checked what mode it ran in.

Learned here: the backfill covered 196 of 636 vectors and skipped every column the recruiter ranks against — running it as written would have made ranking worse than the all-hash state it was fixing.

28A verified fact has a shelf life; bind the verdict to the version

Verification answers "does this match the source" at one moment, against one version. It does not answer "is the source still current" — a different question that nothing in the check touches. The failure is quiet by construction: the fact was genuinely verified, the evidence is real, the provenance is clean, and the answer is now wrong. Nothing throws, because nothing changed on our side. Something changed on theirs.

Do

  • Store when and against which version a fact was verified, not merely that it was. A verdict without those two fields cannot be aged, cannot be invalidated, and will be read years later as if it were fresh.
  • Let a new version invalidate the old verdict rather than inherit it. When a source gains a version, every claim carried against the prior one reverts to unverified until re-checked. Inheriting is the whole bug: it converts "was true" into "is true" with no step where anyone decided that.
  • Separate the two claims in the data model and in the UI. "Quote matches the cited passage" and "that passage is still operative" are different assertions with different evidence. A claim can be perfectly cited and out of date, and a reader who sees only the first will assume the second.
  • Re-verify on read when staleness costs more than the check. Cheap re-checks against a stored source should not be cached at all; the caching is what creates the exposure.
  • Prefer the newest version as the source of truth for contact and routing data — the fields most likely to drift are precisely the ones nobody re-reads.

Avoid

  • Treating a verification result as a permanent property of a fact; showing a once-verified stale claim with the same confidence as a fresh one; citing the oldest document you found because it parsed cleanly.

Learned here, while finding real people to interview. A certificate of service in IURC Cause No. 45591 (July 2021) gave AES Indiana's counsel as tnyhart@btlaw.com — filing-verified, sworn, correct at the time. The 2026 filing in Cause No. 46394 gives tnyhart@taftlaw.com. Same person, same role, different firm; the firm changed and no document announced it. Both addresses were "verified against a public filing" and only one works. Had we written the first into an outreach log and moved on, the email would have bounced with a provenance note beside it saying the address was confirmed.

Load-bearing for this product, not just for this repo: it is the argument for scoping every citation to a proceeding version (ADR-004, ADR-005) rather than to a proceeding. An analyst reading a claim cited to the draft, months after the final order landed, gets a correctly-cited answer to a question they are no longer asking.
