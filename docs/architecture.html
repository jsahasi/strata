Architecture

Components and their boundaries, the data flow from raw document to screen, and where each responsibility lives under app/. This document describes what is built. Where something is designed and not built, it says so in the same place it would have described it. Where a decision is still open in docs/.ai/decisions.html, it says that too, rather than quietly picking an answer and hiding the seam.

The shape in one sentence. A pipeline of small, mostly deterministic stages, with exactly one module permitted to call a model on the pipeline path and exactly one function permitted to decide that a stored claim may be asserted. Everything else is either pure computation or a thin read and write against stored state. The seams between stages are the module boundaries under app/.

This document had gone stale once already — it was last revised at 97daf02 and described a module layout that eight commits had moved. Two habits follow from that. Numbers carry the command that produces them, so a reader can repeat it instead of trusting it. And work that is written but not committed is not described here at all: as this is revised, a scheduler, a docket fetcher, point-in-time replay and a permissions screen all exist in somebody's working tree, and none of them appears below.

Data flow — raw document to screen

The reasoning matters more than the boxes. Three properties of this pipeline do the actual work:

  1. The model sees a diff, never a pair of documents. By the time interpretation runs, diff has already decided what changed. The model is never asked "did anything change" — a question it answers unreliably on long documents — only "does this specific change matter," a smaller and checkable question (ADR-004).
  2. Nothing leaves state as fact without passing through verification. There is one function that turns a stored claim into something a screen may assert — verified_claims() in app/state/claims.py — and every reader goes through it: the change view, the public share page, the assistant's change_detail and search_claims tools. A bug anywhere upstream produces a withheld claim with a reason code, not a wrong fact in front of the analyst.
  3. Every arrow into interpretation and out of it crosses a typed boundary — Change objects in, candidate claims with citations out. Neither side needs to know how the other is implemented. That is what makes each stage swappable on its own.

Dependency direction runs one way for the core. ingestion knows nothing about diff; diff knows nothing about interpretation; interpretation knows nothing about the gate's pass or fail logic, only that it must emit a citation for anything it wants to survive. verification knows nothing about models, databases or the web. This is what makes "fix the class, not the line" tractable — a bug in one stage cannot silently depend on behavior in another, because the only thing that crosses a boundary is a typed object. Above the core the direction is looser and the next diagram draws it honestly, including the edges that run back up.

Ingestion path

Ingestion takes raw text for one document version — a proceeding filing or a company-context document — and produces two things: a DocumentVersion row carrying a SHA-256 of the exact bytes ingested, and a sequence of Passage rows, each a contiguous span of that text with a stable (char_start, char_end) into it. The SHA exists so that "this is the document the citation points at" is checkable independent of anything the database says — if the stored source ever diverges from what was ingested, the hash catches it. Passage boundaries follow the document's own structure (paragraph, then section, falling back to a fixed-size window for unstructured text) because that is the unit the model would later be shown and the unit any index would take — but the boundary choice is a retrieval convenience, not the unit of truth, and app/ingestion/ingest.py says so in those words. The unit of truth is the raw text plus an offset into it, which is why ingestion never rewrites, trims, or re-encodes the source before storing it. Anything ingestion normalizes (whitespace collapse, smart-quote folding) it normalizes in a documented, tested function that verification also calls — the same normalization on both sides of every comparison, or the comparison means nothing.

The passage store, and why offsets are the unit

Every claim in the product — a diff segment, a citation, a piece of obligation evidence — ultimately resolves to (document_version_id, char_start, char_end) against an immutable, hashed source. Offsets are the unit rather than passage IDs, sentence IDs, or a similarity score, for one reason: an offset is checkable by exact substring lookup. No embedding math, no fuzzy threshold, no model in the loop — read the bytes between two integers and compare them to what was claimed. That is what makes verification a pure function instead of another place where the product has to trust something.

Offsets are addressed against the frozen version, not the current document, so a citation minted against version 3 stays valid even after version 4 exists — versions are never edited in place, only appended.

The store carries no index, and this paragraph used to say it did. ADR-008 designs the split — lexical BM25 over docket text, semantic matching only where paraphrase matters, over the company-context join — and none of it is built. The ADR carries implementation: none for exactly this reason. Check it rather than trusting it: grep -rniE 'fts5|bm25|embed|vector|tfidf' app/ returns nothing on any of those terms. The nearest thing to search in the product is search_claims in app/chat/tools.py — a substring scan over rows the tenant chokepoint already returned, re-verifying each citation as it goes. No index, no scoring, and it does not pretend otherwise. The one similarity computation anywhere in the codebase is difflib.SequenceMatcher inside app/diff/engine.py, which scores a detected change's confidence; it is not retrieval, and the verifier refuses to use similarity at all.

When retrieval is built, it ranks which passages interpretation gets to see; it does not decide which changes exist. That distinction is what keeps a retrieval miss a quality problem instead of a coverage problem — see diff, next.

The rule the chokepoint states is narrower than "every tenant read goes through one file", and stating it accurately is what makes it enforceable. It is: there is one definition of what an unscoped read is, and no module writes a second one. Twenty-four modules import _require_scope; none copies it. That is checkable in one line — grep -rn "_require_scope" app/ | grep -v "def _require_scope" — and a copy would show up as a second def.

Six functions are the honest exception, and both files carrying them say so in a comment rather than in a commit message: four private scoped reads in app/web/views/admin.py and two in app/chat/tools.py. They were written while queries.py was being edited by somebody else and moving them would have lost that work. They import the guard, and their signatures already match the ones queries.py uses, so the move is a handoff and not a rewrite. It is still owed.

The diff engine — pure, testable, no model dependency

Diffing is the one stage in this pipeline built to have a single correct answer per input, so it is built as a pure function: diff(passages_v_n_minus_1, passages_v_n) -> list[Change]. No network call, no model, no clock, no randomness. Given the same two passage sequences it returns the same Change list every time, which means it can be unit-tested directly against the synthetic corpus's deliberate edits — the corpus labelled T3 under data/ — with the expected answers read from data/manifest.json rather than from the code under test. The test asserts an exact expected diff, not a fuzzy "looks about right."

Each Change is typed — added, removed, or modified — and carries passage references on both sides (or one side, for pure additions or removals), so nothing downstream needs to re-derive what moved. This is also where the sharpest known failure mode lives: alignment degrades when a document is restructured wholesale — sections renumbered, text relocated rather than edited. The design does not pretend this is solved. A passage that reads almost identically but sits under a different section number has its confidence capped at 0.5, a ceiling chosen to fall below any plausible escalation threshold so a renumbering can never present itself as a settled match (ADR-004). The cap is real; the floor that would act on it is not. MIN_CONFIDENCE_BP ships at 0, so a capped alignment is recorded as low confidence and escalates nothing. Half the mechanism is built, and saying it escalates today would be the confident-and-wrong claim. Because the algorithm is swappable behind the Change contract, a better aligner for restructured documents is a diff/-internal change later, not a rewrite of interpretation or verification.

Interpretation — the only place on the pipeline path that calls a model

Every other stage in this pipeline is deterministic on purpose, so that the one stage that is not — interpretation — is easy to find, easy to isolate, and easy to blame first when something is wrong. Every function in it that calls a model is named plainly, and the provider's client is imported inside the factory function rather than at module load, so the package imports cleanly on a machine with no SDK installed.

Interpretation does four jobs, all downstream of a Change the diff engine already found: judge materiality; extract obligations with evidence spans; map a change to the company-context obligations, projects, and documents it affects; recommend an action and a reviewer. Draft-versus-final is read once, from the version's explicit status field, and used to dispatch to one of two branches before any model call happens — a draft change is only ever asked to produce monitor-or-comment language, a final change is only ever asked to produce comply language with an effective date. The model is never asked which branch it is in, because that is exactly the distinction ADR-005 says must never be inferred. That dispatch lives in action.py: 35 lines, no imports, and it raises rather than defaulting when it meets a status it does not know.

Not everything in this stage calls a model. Routing to the obligation owner — the named person recorded on the obligation record — is a deterministic lookup against that field, in app/state/routing.py, not a guess. The fewer decisions handed to the model, the fewer things the gate has to catch, and the fewer things can be wrong in a way that reads as confident.

What interpretation emits is never a fact. It is a candidate claim: text, a citation of (version_id, char_start, char_end, quoted_text), and a confidence. That object crosses the one boundary in the system where a hallucination could enter — which is exactly why the gate exists.

Two things are settled since this section was last written, and one is not. The model is settled: claude-opus-5, pinned as a constant in propose.py and deliberately not read from the environment, so a deployment cannot quietly swap the thing that produces text without a commit (ADR-37). How the key reaches the process is settled: app/config.py loads .env at startup, real environment first. Before it existed, every model path announced itself off while a valid key sat in the file the README told the reviewer to put it in — a fallback firing honestly and the product still wrong, which is the worst shape a bug can take. What is not settled is whether the proposer works. Nothing in app/ calls it, no run has been made against the real API from this repository, and until one is, the module is unexercised code sitting behind tested code. Its own docstring says that.

Verification — the gate, and it sits on the read path

app/verification/verifier.py answers one question: does the text at these offsets, in this version, equal this quote after normalization? Not similarity, not a threshold, equality — plus an occurrence check, so a quote that appears three times in a version cannot cite the wrong one. It calls no model, opens no socket, and imports only app/text/normalize.py. That is what lets the module the product's trustworthiness rests on run in CI with no API key, no network and no database, and it means a model that misquotes fluently is caught by code that cannot itself misquote, because it generates nothing.

The gate is a read, not a write, and the difference is the whole design. The function every reader goes through is verified_claims(session, company_id, change_id) in app/state/claims.py. It fetches the change's claims, re-reads each cited source, calls the verifier, and returns two lists: what may be asserted, and what may not. It writes nothing and stores no verdict. There is no verified column anywhere in the 43-table schema, on purpose — a stored boolean is a promise about bytes that may have changed since, and ADR-003 refuses to make it. Edit a source after a claim was written and that claim flips to withheld on the next page load, with no migration and no background job.

Three readers use it and none has its own copy: the change view in app/web/views/changes.py, the public share page (which re-verifies at open time, every open), and the assistant's change_detail and search_claims tools. A withheld claim's wire form is built in one function and carries a reason code, a reason text and where it sits — never the statement, never the quote.

The confidence floor is not in the verifier and never was. The verifier's own docstring says a threshold would defeat the point of having a gate. What exists is one number, MIN_CONFIDENCE_BP in app/state/claims.py, read from STRATA_MIN_CONFIDENCE_BP in basis points, applied after the citation check so a claim that misquotes reports the misquote rather than a number. It ships at 0 — no claim is withheld for confidence alone — because there is no evidence yet for where the line sits, and a figure picked to look rigorous is worse than an honest zero. The mechanism is configuration rather than a constant so that setting it is a deployment decision and not a code change (ADR-006).

State and audit

This section described a system that was never built, and the correction is worth more than the original. It said project state was a projection folded from an append-only event log, that the escalation queue was a read over that log, and that rollback was a replay to an earlier point. None of that is true. State is ordinary SQLAlchemy tables mutated in place. escalations is a table; resolving one stamps resolved_at and resolved_by on the row. The event-fold-versus-snapshots question that paragraph called open was settled by ADR-16, ADR-17 and ADR-31, and settled the other way.

What actually carries the evidence is a hash-chained audit log beside the tables, not underneath them. Every act that matters appends a row to audit_events: the actor, the action, the subject, the previous row's hash, and a digest over its own fields. A SQLAlchemy before_flush listener refuses any UPDATE or DELETE of an audit row, so the append-only rule binds this process at the point of writing rather than living in a comment. verify_chain(session, company_id) walks the rows in sequence order and raises AuditTamperError on a sequence gap, a broken prev_hash, an altered row, or a digest scheme it cannot compute.

Taking a decision back is a row, not a replay. revert_event() in app/state/rollback.py restores the state the decision changed and then appends an event naming the one it undoes, in that order, inside the caller's transaction. Neither row is edited, both stay in the chain, and the chain verifies over both. One sentence in that module is worth repeating here: reverting a decision restores state, and it never turns a withheld claim into an assertion — only the source agreeing with the quote does that. Point-in-time replay does not exist. Rebuilding the state as it stood at an earlier sequence number is a different capability and no module under app/ offers it.

What changes when this outgrows SQLite

ADR-007 picks SQLite so the submission starts with one command on a reviewer's machine. ADR-28 revisits it and names the trigger for moving: a second tenant, or any real customer data, whichever comes first — not a date and not a row count. SQLite does not scale as built, and this section says plainly where it breaks and what the fix is, not as a hedge but because implying otherwise would be exactly the kind of confident-and-wrong claim the rest of this design refuses to make.

  • Concurrent writers. SQLite serializes writes to a single file. WAL mode would let readers proceed during a write, and WAL is not enabled — nothing in this repository sets journal_mode, so a reader waits behind a writer today. The deployment runs one uvicorn worker for exactly this reason, which is the ADR-28 trade-off arriving in production rather than being papered over. The fix is Postgres, and SQLAlchemy makes that a connection string, not a rewrite — but transaction and locking behaviour differ enough that the switch needs its own test pass, not just a config flag.
  • Horizontal scale of the web tier. A SQLite file lives on one disk; two app instances behind a load balancer cannot share it without contention. Postgres removes this by being a server rather than a file.
  • Retrieval, lexical and semantic. Neither exists, so neither has a scaling problem yet. When ADR-008 is built, the lexical side would start as SQLite FTS5, which is process-local to one file and becomes Postgres full-text or a shared index; the semantic side over the company-context join is small enough to compare in process before it needs a vector store. Both plug in behind one retrieve() call beside passages_for_company, which is the whole reason that read is a function and not an inline query.
  • The audit chain. verify_chain walks every row for a company on every call. That is linear in the log and fine at demonstration size; at real volume it becomes a walk from the last verified checkpoint, which needs a published head to anchor to. Compaction is not the answer here — dropping rows is the one thing this table exists to prevent.
  • Read-time verification. The gate runs once per claim per view. That is the cost of having no stored verdict, and it is paid in CPU against a source text already in the page's working set. At volume the answer is a cache keyed on the source hash, which invalidates itself when the bytes change — not a stored boolean, which does not.
  • Background work. Ingesting a long proceeding runs synchronously today, inside the pipeline chokepoint, called from a request. The real corpus makes the number concrete: a million-character filing against its correction produces 144 changes in 0.78 seconds. At volume this becomes a queued job so a large upload does not hold a request thread open; the chokepoint's shape does not change, only what calls it.

Configuration, schema migration, and the deploy

This section did not exist when the application ran only on a laptop. It exists because two defects were found by deploying, and neither could have been found by a test.

The first was configuration that never arrived. Three modules read their settings from os.environ and each falls back safely when it finds nothing: the assistant says it is unavailable, the proposer declines to propose, the mail transport declines to send and says so. All three announce the fallback, which is right. What was wrong is that they announced it always — the key lived in .env, nothing put .env into the environment, and a deployment holding a perfectly good key behaved exactly like one holding none. Every fallback fired, every message was honest, and the product was still wrong. app/config.py is the fix: fifteen lines of standard library, called at the top of app/main.py before app.state or app.web is imported. A variable already in the environment is never overwritten by the file, because a container or an export is a deliberate act and a file on disk is a default. It returns the names it set and never a value; that file holds an API key, an OAuth refresh token and a client secret, and a helpful startup line echoing them would put all three into every log the host ships to.

The second was a deploy that ran no migration. deploy/entrypoint.sh seeded only when there was no database, which is right — a redeploy must never lay demo rows over an audit chain. But when the file existed it ran nothing, not even create_all. The first deploy after a column was added would have kept the old table while the new code selected the new column, and every proceeding, claim and verification screen would have answered no such column: document_versions.source_url. No test could catch it: tests build their schema from the current models every time, so they never meet yesterday's database. It appears only in production, on the deploy, in front of whoever is looking.

The obvious fix is five ALTER TABLE lines. That fixes the instance and leaves the class — the next column anybody adds breaks the deploy the same way, and they will not think of this file. So app/state/migrate.py derives the difference instead of listing it: ask SQLAlchemy what the models declare, ask the database what it has, add what is missing. New tables through create_all, new columns through a generated ALTER TABLE ... ADD COLUMN, new indexes through CREATE INDEX IF NOT EXISTS. It never drops, renames, retypes or backfills. A new column is NULL on old rows, because NULL says the schema of the day did not record this and a default says something the record cannot support. And it refuses rather than guessing: a NOT NULL column with no default on an existing table goes into a refused list, scripts/migrate.py prints each refusal to stderr and returns 1, and set -eu in the entrypoint stops the deploy rather than starting the application against a schema it cannot read.

The application surface

The pipeline above is the reason the product can be trusted. It is not what a person uses. Five capabilities sit on top of it, and each one is described here by what it does and by what it does not.

Clarke — the assistant

app/chat/ is the second and last place in the codebase that calls a model. The persona is a commission's records clerk (ADR-50): it finds a project, opens a change, says what moved, and offers no opinion on the merits. It has ten tools — eight reads and two writes — and the boundary is the interesting part. The model never holds an identity. company_id, actor, user_id and session are supplied by the caller, and if the model puts any of them in a tool call the turn is refused rather than the argument stripped, with an audit row to say it happened (ADR-51). The tool registry checks itself at import: a tool whose signature disagrees with its allowlist, or that names a permission code the product does not define, fails the import rather than the request.

Two limits are worth stating plainly. The claims Clarke reads are gated — change_detail and search_claims go through verified_claims(), and a withheld claim reaches the model as a reason code with no statement and no quote. The prose Clarke writes is not gated. Nothing re-checks the reply text against the source. The controls are the persona prompt, the narrowed payload, and a check that a turn which withheld something says so with the count; app/chat/tools.py concedes it in one line — "a tool result is text a model will summarise, and nothing in this file can stop it paraphrasing badly." Second: history is stored, ordered by an ordinal with a unique index rather than by a timestamp, and the engine discards it before the model sees it. Each turn stands alone today.

Share links

/s/{token} is the only unauthenticated route in the product, and the token is the whole credential. The row stores a SHA-256 of it and never the token itself; the plaintext exists once, on the object returned to the person who minted it. Expiry is mandatory, seven days by default and thirty at most, and a request for zero or for a year is refused rather than clamped. Expired, revoked, unknown, and "this tenant switched sharing off" all render one identical 404, so nobody can probe which tokens are real. A share re-verifies its claim at open time, on every open, through the same function every screen uses — so a shared claim whose source later changed shows as withheld to the recipient without anybody revoking anything.

The defect that made this route public is worth keeping in the record. /s/ was not on the anonymous-allow list, so the session guard answered 303 to /login?next=%2Fs%2F<token> — putting a live bearer token into a query string, where it reaches the access log, the Referer header and the browser history. The fix was one prefix, with its trailing slash, so /settings and a bare /s stay guarded.

Invitations, and no signup

There is no registration route anywhere in app/. An account is provisioned by an administrator holding user.manage, or handed off by somebody holding user.invite when routing finds an obligation owner with no login. Two clocks: seven days for a handoff, twenty-four hours for a provision. An inviter can never grant more than they hold. A resend is a new invitation with a new token and the old row marked superseded, never a longer life on the same one. app/state/invites.py sends no mail — it returns the token once, to its caller — and the token goes into the link and nowhere else. At this commit /invite/ is not on the public-path list, so an invitee is sent to a login page they have no account for. The admin screen renders the warning itself, and it asks is_public_path() rather than assuming, so the warning will disappear on its own the day the prefix is added.

Integrations

/admin/sources is a registry, not a connector, and the page says so in its own copy rather than only in a comment: "Nothing in this build fetches on a schedule." The list of fetchable source kinds is an empty tuple, so can_fetch() answers no for every kind and every new row is born with status not_implemented. What is real: rows with a kind, a status, an enable flag, provenance counts, and an audited history of every registration, edit and removal. Credentials are stored as the name of an environment variable, allow-listed by prefix and shape, and the screen shows whether that name is set in this process — never the value, never its length. There is no "test connection" button, and the page explains why: a button that fetches an administrator-typed URL is a request-forgery surface. What exists instead is a text-only preflight that refuses private ranges and internal-looking names, opens no socket and resolves no name, and says so on every verdict.

The first-login tour

Five stops, ending on a withheld claim and then the assistant. The stops are data in the template; the script holds behaviour and no words. State is a cookie and nothing else — no route, no table, no column — because a preference is not a credential, and it therefore may not share a name, a lifetime or a reader with the session cookie. A stop whose target is not on the screen is skipped, and if no stop resolves, nothing is drawn and nothing is remembered. base.html does not include it, so it reaches nobody. That is asserted rather than forgotten: the test that would prove it wired carries a strict expected-failure marker naming the gap.

The two corpora

There are two, both labelled, and conflating them would be the easiest dishonesty available to this product.

The synthetic corpus — three versions of a fictional proceeding under data/, with a manifest — carries traps built on purpose: one sentence repeated three times per version so an unqualified citation is ambiguous, and a wholesale restructure that scores 0.944 on raw text similarity while meaning something different. It stays, and it stays the eval corpus (ADR-40). The expected answers live in data/manifest.json rather than in the code under test, so the oracle is independent of the thing it scores. Real filings will not reproduce those traps on demand, so replacing the fixture would quietly gut the harness. The synthetic corpus must never be given a source URL: no commission published it, and a plausible-looking docket link would be the product inventing provenance, which is the one failure everything else here exists to prevent.

The real corpus — 102 public filings under data/real/, from eight commissions across nineteen dockets. Every filing has a provenance record beside it carrying the source URL, the docket, the filing date, the filer, how it was obtained, the retrieval time and a SHA-256 of the saved bytes. The record shapes are not uniform, and where a field is absent the record says nothing rather than guessing. One pair is loaded into the demonstration by scripts/ingest_real.py: Kentucky PSC 2025-00113, a witness's direct testimony filed and then corrected. 1,024,409 characters against 1,024,536 — 127 characters of difference across a million, and the pipeline finds 144 changes in 0.78 seconds. That number is the argument, because it states the problem as arithmetic on a document somebody really filed, with a link back to the commission's own copy so a reader can leave and check. The filer also published a marked-up version saying what they changed, which is ground truth nobody on this side wrote.

One claim in the demonstration comes from that real pair, and it was written by hand, not extracted — the script says so. Nothing in this product extracts claims yet.

Open questions this document does not resolve

Two of the three questions this section used to carry are closed, and closing them honestly matters more than the list looking long.

  • Closed — which model, and how the key reaches it. claude-opus-5, pinned as a constant in both places that call one, deliberately not read from the environment (ADR-37). The key arrives through app/config.py. Every model path still announces its fallback by name when there is no key.
  • Closed the other way — event-fold versus snapshots. Settled by ADR-16, ADR-17 and ADR-31 as an append-only hash-linked audit log beside mutable tables, with a correction written as a new row that supersedes an old one. This document argued for a projection folded from an event log and described the product as if that had been built. It had not.
  • Open — where the confidence floor sits. It ships at 0 basis points, which withholds nothing for confidence alone. app/state/claims.py says why in its own words: there is no evidence yet for where the line sits, and a number picked to look rigorous is worse than an honest zero. Finding the number is an eval question, and the eval harness scores diff and verification, not confidence.
  • Open — does the proposer work. app/interpretation/propose.py has never run against the real API from this repository. Until it has, it is unexercised code behind tested code, and no claim on any screen comes from it.
  • Open — retrieval. ADR-008 is accepted and unbuilt. Nothing under app/ indexes, ranks or embeds anything. The design says where it plugs in; that is not the same as it existing.
  • Open — the migration has no test. Named again here because it is the one gap that can take a live site down, and because a document that lists its gaps in a diagram caption and not in the list at the end is hiding them in plain sight.

None of these change a module boundary. They are calibration, coverage and unfinished work, which is exactly why the boundaries above were drawn to keep them swappable.
