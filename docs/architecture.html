Architecture

Components and their boundaries, the data flow from raw document to routed action, and where each responsibility lives under app/. This document defines the target architecture; docs/.ai/tasks.html tracks how much of it is built. Where a decision is still open in docs/.ai/decisions.html, this doc says so rather than quietly picking an answer and hiding the seam.

The shape in one sentence. A pipeline of small, mostly deterministic stages, with exactly one stage permitted to call a model and exactly one stage permitted to turn a model's output into fact. Everything else is either pure computation or a thin read/write against stored state. The seams between stages are the module boundaries under app/.

The reasoning matters more than the boxes. Three properties of this pipeline do the actual work:

  1. The model sees a diff, never a pair of documents. By the time interpretation runs, diff has already decided what changed. The model is never asked "did anything change" — a question it answers unreliably on long documents — only "does this specific change matter," a smaller and checkable question (ADR-004).
  2. Nothing reaches state without passing through verification. There is exactly one write path into project state, and it is gated. A bug anywhere upstream produces an escalation, not a wrong fact in front of the analyst.
  3. Every arrow into interpretation and out of it crosses a typed boundary — Change objects in, candidate claims with citations out. Neither side needs to know how the other is implemented. That is what makes each stage swappable on its own.

Dependency direction runs one way, top to bottom of the table above. ingestion knows nothing about diff; diff knows nothing about interpretation; interpretation knows nothing about verification's pass/fail logic, only that it must emit a citation for anything it wants to survive. verification knows nothing about models at all. This is what makes "fix the class, not the line" tractable — a bug in one stage cannot silently depend on behavior in another, because the only thing that crosses a boundary is a typed object.

Ingestion path

Ingestion takes raw text for one document version — a proceeding filing or a company-context document — and produces two things: a DocumentVersion row carrying a SHA-256 of the exact bytes ingested, and a sequence of Passage rows, each a contiguous span of that text with a stable (char_start, char_end) into it. The SHA exists so that "this is the document the citation points at" is checkable independent of anything the database says — if the stored source ever diverges from what was ingested, the hash catches it. Passage boundaries follow the document's own structure (paragraph, then section, falling back to a fixed-size window for unstructured text) because that is the unit the model is later shown and the unit BM25 indexes — but the boundary choice is a retrieval convenience, not the unit of truth. The unit of truth is the raw text plus an offset into it, which is why ingestion never rewrites, trims, or re-encodes the source before storing it. Anything ingestion normalizes (whitespace collapse, smart-quote folding) it normalizes in a documented, tested function that verification also calls — the same normalization on both sides of every comparison, or the comparison means nothing.

The passage store, and why offsets are the unit

Every claim in the product — a diff segment, a citation, a piece of obligation evidence — ultimately resolves to (document_version_id, char_start, char_end) against an immutable, hashed source. Offsets are the unit rather than passage IDs, sentence IDs, or a similarity score, for one reason: an offset is checkable by exact substring lookup. No embedding math, no fuzzy threshold, no model in the loop — read the bytes between two integers and compare them to what was claimed. That is what makes verification a pure function instead of another place where the product has to trust something.

Offsets are addressed against the frozen version, not the current document, so a citation minted against version 3 stays valid even after version 4 exists — versions are never edited in place, only appended. The passage store also carries the lexical index (BM25 over the docket text) and, only for company-context passages, a semantic index — the split from ADR-008. Retrieval ranks which passages interpretation gets to see; it does not decide which changes exist. That distinction is what keeps a retrieval miss a quality problem instead of a coverage problem — see diff, next.

The diff engine — pure, testable, no model dependency

Diffing is the one stage in this pipeline built to have a single correct answer per input, so it is built as a pure function: diff(passages_v_n_minus_1, passages_v_n) -> list[Change]. No network call, no model, no clock, no randomness. Given the same two passage sequences it returns the same Change list every time, which means it can be unit-tested directly against the synthetic corpus's deliberate edits (T3/T6) and the test asserts an exact expected diff, not a fuzzy "looks about right."

Each Change is typed — added, removed, or modified — and carries passage references on both sides (or one side, for pure additions or removals), so nothing downstream needs to re-derive what moved. This is also where the sharpest known failure mode lives: alignment degrades when a document is restructured wholesale — sections renumbered, text relocated rather than edited. The design does not pretend this is solved. A low-confidence alignment is escalated rather than guessed at, the same "absence is denial" rule applied one stage earlier than usual. Because the algorithm is swappable behind the Change contract, a better aligner for restructured documents is a diff/-internal change later, not a rewrite of interpretation or verification.

Interpretation — the only place that calls a model

Every other stage in this pipeline is deterministic on purpose, so that the one stage that is not — interpretation — is easy to find, easy to isolate, and easy to blame first when something is wrong. It is the only module permitted to make a model call, and every function in it that does so is named plainly, so a grep for the provider's client library finds every place the product can be fluent and wrong.

Interpretation does four jobs, all downstream of a Change the diff engine already found: judge materiality; extract obligations with evidence spans; map a change to the company-context obligations, projects, and documents it affects; recommend an action and a reviewer. Draft-versus-final is read once, from the version's explicit status field, and used to dispatch to one of two branches before any model call happens — a draft change is only ever asked to produce monitor-or-comment language, a final change is only ever asked to produce comply language with an effective date. The model is never asked which branch it is in, because that is exactly the distinction ADR-005 says must never be inferred.

Not everything in this stage calls a model. Routing to the obligation owner — the named person recorded on the obligation record — is a deterministic lookup against that field, not a guess. The fewer decisions handed to the model, the fewer things verification has to catch, and the fewer things can be wrong in a way that reads as confident.

What interpretation emits is never a fact. It is a candidate claim: text, a citation of (version_id, char_start, char_end, quoted_text), and a confidence. That object crosses the one boundary in the system where a hallucination could enter — which is exactly why the next stage exists.

Verification — the gate

Verification takes a candidate claim and does one job: decide whether it is allowed to become fact. It re-reads the passage store at the exact offsets the claim cited, for the exact version the claim cited, runs both the stored substring and the claimed quote through the same normalization ingestion used, and compares them for equality — not similarity, not a threshold, equality. A claim whose quote does not match what is actually at those offsets, or whose confidence sits below the configured threshold, is written to the escalation queue with the specific reason (mismatch or low confidence), never silently dropped and never shown to the analyst as settled.

This module has no model dependency of its own, which is deliberate twice over: it means the module the product's trustworthiness rests on can be exercised in CI with no API key and no network, and it means the failure mode the product is built around — a model that misquotes fluently — is caught by code that cannot itself misquote fluently, because it does not generate anything. It only compares. state has exactly one write path for claims, and it runs through here.

State and audit

Project state — the current obligations, projects, documents, changes, and actions the analyst sees as true — is a projection over an append-only event log, not a table mutated in place. Every write that reaches state through verification is one event; every reviewer decision (approve, reject, amend) is another. The escalation queue is not a separate table kept in sync by hand — it is a read over the same log, defined as "candidates with no resolution event yet." Approving or rejecting an item is appending an event, not deleting a row, so the queue cannot drift from the log that explains it.

An event log gives audit history and rollback the same mechanism: rollback is replaying the projection up to an earlier point in the log, and audit is reading the log directly. That is this document's working answer to the open question in decisions.html (event-fold versus snapshots) — chosen because a 48-hour build with a small corpus never needs the alternative's main benefit, fast replay over a long log, and one mechanism serving two requirements is less to get wrong than two. This is not yet written back into the ADR log as accepted — it is the architecture's current default, and if replay cost becomes visible against the synthetic corpus, periodic snapshot compaction is the documented escape hatch, not a redesign.

What changes when this outgrows SQLite

ADR-007 picks SQLite so the submission starts with one command on a reviewer's machine. It does not scale as built, and this section says plainly where it breaks and what the fix is — not as a hedge, but because implying otherwise would be exactly the kind of confident-and-wrong claim the rest of this design refuses to make.

  • Concurrent writers. SQLite serializes writes to a single file; WAL mode lets readers proceed during a write but writers still queue behind each other. Fine for one analyst team exercising the demo; wrong the moment more than one tenant is ingesting or resolving escalations at the same time. The fix is Postgres, and SQLAlchemy makes that a connection string, not a rewrite — but transaction and locking behavior differs enough that the switch needs its own test pass, not just a config flag.
  • Horizontal scale of the web tier. A SQLite file lives on one disk; two app instances behind a load balancer cannot share it without contention. Postgres removes this by being a server rather than a file.
  • Lexical retrieval. SQLite's FTS5 index is process-local to that one file. At scale this becomes Postgres full-text search or a dedicated search index shared across instances — the swap happens entirely inside app/passages/, per the module table above.
  • Semantic retrieval. There is no pgvector today because ADR-008 only asks for semantic matching over the company-context join, which is small enough to compare in process. At real volume that needs a vector store, and the retrieval interface in app/passages/ is exactly where it plugs in.
  • The event log. Replay cost grows with log length. The documented answer above — snapshot compaction — is the fix, not a switch to storing state as mutable rows, which would give up the audit guarantee the log exists for.
  • Background work. Ingesting a long proceeding runs synchronously today, inside the pipeline chokepoint, called from a request. At volume this becomes a queued job so a large upload does not hold a request thread open; the chokepoint's shape does not change, only what calls it.

Open questions this document does not resolve

Carried forward from decisions.html because pretending they are settled here would contradict that log: which model interpretation calls, and its fallback when unavailable; where the confidence threshold in verification actually sits, and on what evidence; whether the event-fold default above survives contact with the eval corpus. None of these are architectural in the sense of changing a module boundary — they are configuration and calibration, which is exactly why the boundaries above were drawn to keep them swappable.
