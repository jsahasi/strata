Web Surface and Deployment

The design for what a reviewer sees at strata.sudama.ai, and how it gets there. Written 2026-08-03, before implementation.

This document covers only what is new: the web layer, its visual design, and the deployment. The pipeline behind it — ingestion, diff, interpretation, verification, state — is specified in docs/architecture.html and is unchanged by anything here. The reasoning for each choice below lives in docs/.ai/decisions.html as ADR-009 through ADR-014; this document says what is being built, not why it beat the alternatives.

Sequencing risk, stated first because it governs everything else. app/ and tests/ are empty at the time of writing. The web layer renders state that nothing yet produces. Build order is therefore verifier and diff before screens, and the deployment before the design polish — a designed shell over an absent product is the exact failure this design was chosen to avoid. If hours run short, the cut order is in the last section.

Scope

Three additions.

WhatWhereDetail
Web layerapp/web/FastAPI routes, Jinja templates under app/web/templates/, assets under app/web/static/. A read surface over stored state, plus exactly two writes: approve and reject on a queued item. The module boundary is the one already fixed in docs/architecture.html — deliberately thin, no business logic.
Design systemapp/web/static/strata.cssOne stylesheet. Design tokens, type scale, both colour schemes. No framework, no icon font, no build step.
DeploymentDockerfile, compose.yml, CaddyfileTwo containers on a dedicated droplet. Caddy terminates TLS; the app serves on an internal port.

The web layer holds no business logic. It reads projections and renders them. Anything that decides something belongs upstream, behind the verification gate.

Screens

Four. Each maps to a moment in the analyst's day; a screen that does not is not built.

ScreenRouteWhat it answers
Proceedings/"What am I tracking, and where has something moved?" One row per proceeding: docket, jurisdiction, latest version, draft-or-final badge, count of unreviewed changes.
Proceeding detail/proceedings/{id}"What changed between these two versions?" A version timeline, and the typed changes between any selected pair — added, removed, modified — each with its materiality and its draft-or-final status.
Change detail/changes/{id}"What does this mean for us, and can I trust it?" The claim, its citation, the obligations and projects it touches, the recommended action, the named reviewer.
Review queue/review"What did the system refuse to assert?" Everything that failed verification or fell below the confidence threshold, each with the reason stated in plain words.

Deliberately absent: a settings page, a metrics dashboard, an admin view, a search box, a user profile. None answers a pain the analyst named, and each would dilute the one path the demo depends on. The internal eval numbers live in the submission documents, not in the product — an eval dashboard built for a non-technical user is a feature the panel is explicitly primed to challenge.

The citation viewer

This is the interaction the submission rests on, so it is specified rather than sketched.

Every claim on change detail carries a citation chip showing the section reference. Activating the chip opens a source panel beside the claim, scrolled to the cited character offsets, with the exact quoted span marked in the original document text. The analyst reads the sentence where it actually appears, and closes the panel. No modal, no navigation away, no loss of place.

  CHANGE DETAIL                              SOURCE PANEL (opens on chip activation)

  |  Threshold lowered, 20 MW -> 10 MW    |   |  SECTION 2. DEFINITIONS            |
  |                                        |   |                                    |
  |  Materiality: MATERIAL                 |   |  2.1 "Large Load Customer" means   |
  |  Status: FINAL - effective 2026-11-01  |   |  a Customer whose Requested Load   |
  |                                        |   |  equals or exceeds [10 megawatts]  |
  |  "...equals or exceeds 10 megawatts"   |   |  ^^^^^^^^^^^^^^^^^^^ marked span   |
  |  [ Sec 2.1, v3 ]  <- citation chip     |   |  (MW).                             |

  |  Action: COMPLY   Reviewer: J. Okonkwo |   |  maximum electric demand...        |

The paired demonstration. Two changes, shown one after the other. The first verifies: the chip is solid, the span highlights, the claim reads as established fact. The second carries a deliberately corrupted quote. It never renders as a claim at all. It appears in the review queue, labelled with the reason and showing the mismatch — what was quoted, against what the source actually says at those offsets.

Constraint on the visual design, and it is a hard one. Verified and unverified must not read as two shades of a single treatment. A greyed-out assertion is still an assertion — the reader's eye completes it. The unverified state has to differ in structure, not only in colour: the claim text does not appear in the position where claims appear, and what occupies that position is the reason it was withheld. It must work without a legend, and it must survive being screenshotted in black and white.

Design system

One stylesheet, organised as tokens then components.

  • Type. A scale built for dense regulatory prose, not for dashboard chrome. Quoted source passages need a real measure — around 66 characters — and generous leading, because the analyst reads them rather than scans them. Interface text and document text are visibly different registers, so a quotation is never mistaken for the product's own voice.
  • Colour. Greyscale carries the structure. One accent for interactive elements, one for escalation. Materiality and draft-versus-final are conveyed by label and weight first, colour second, so the meaning survives colour blindness and a monochrome screenshot.
  • Both schemes. Light and dark, via prefers-color-scheme. Tokens are declared once and inverted, not redefined per component.
  • No dependencies. No CSS framework, no icon font, no web font fetched from a third party. System font stack. Every byte the page loads is served from the same origin, which also keeps the content security policy simple.

The visual execution runs under the frontend-design skill at implementation time. This section fixes the constraints that skill works within.

Deployment

  strata.sudama.ai  --A record-->  [ new droplet, nothing sensitive on it ]
                                     |
                                     |  :443  +-----------+
                                     +------->|   caddy    |  TLS via Let's Encrypt,
                                              |            |  basic-auth at the edge
                                              +-----+------+
                                                    | :8000 (internal only)
                                              +-----v------+
                                              |   strata    |  FastAPI, uvicorn
                                              |             |  seeds corpus if DB empty
                                              +-----+------+
                                                    |
                                              +-----v------+
                                              |  volume     |  SQLite
                                              +------------+

Properties. Two containers, one compose file. SQLite on a named volume, so a redeploy does not lose reviewed state. The corpus seeds on first boot only if the database is empty. Basic auth at the edge, with the credentials printed in the submission — this keeps crawlers and strangers out without putting a login screen between a reviewer and the demo.

The local contract survives untouched. The Dockerfile calls the same entrypoint as make run. There is no deployment-only code path, because a deployment-only code path is a thing that breaks the moment nobody is testing it. make test stays offline and does not know the droplet exists.

Failure behaviour

The deployed instance obeys the same rule as the local one: absence is denial. Deployment must not become the place that principle quietly stops applying.

ConditionBehaviour
Database emptyThe page says the corpus has not loaded, and how to load it. It does not render an empty table that reads like "nothing has changed".
Verification cannot runNo claim renders as established. Everything routes to review. The product degrades to useless-but-honest rather than confident-and-wrong.
Model unavailableIngestion, diff and citation verification continue — they need no model. Interpretation degrades visibly to escalation, with the reason shown, per principle 26: a fallback must announce itself.
Citation offsets out of rangeTreated as a verification failure, not an exception. The claim is withheld and the reason names the version and the offsets.

Testing

Existing suite unchanged: offline, deterministic, asserted against the corpus manifest's known answers. Deployment adds three checks and no more.

  1. /healthz returns 200 with the schema version and the corpus row counts.
  2. A container smoke test: build the image, boot it against an empty volume, confirm the seed runs and the known change count matches the manifest.
  3. A rendering test for the withheld state — a claim whose citation fails must not appear in the change-detail response body at all. This is asserted against the HTML, because "it looked greyed out" is not a guarantee and a CSS change could otherwise silently reveal it.

Cut order, if hours run short

Sacrifice in this sequence, and say so in the submission rather than hiding it: dark scheme; the review queue's amend action, keeping approve and reject; the proceedings list, entering at a single seeded proceeding instead; the deployment itself, falling back to the local run which is still guaranteed.

Never cut: the citation viewer, the withheld-claim state, or the paired verified and corrupted demonstration. Those three are the submission's argument. Everything else on this page is in service of them.

Part two — glass on the chrome, paper for the record

A constraint the brief did not mention, and it is load-bearing. tests/test_chat_surface.py::test_the_dock_borrows_the_apps_palette_rather_than_inventing_one and its twin in tests/test_tour.py assert that clerk.css and tour.css contain no hex literal and no rgba( followed by a digit, outside comments. So a translucent value cannot be written in either file. Every alpha, every blur, every shadow below is declared once in strata.css as a custom property, and the other two sheets reference it with var() and nothing else. Break this and the suite goes red at 1256.

Five new values, and what each is for

Two hues exist in this product and that is the argument on line 11 of the stylesheet. Every value below is achromatic or sits in the same cool-grey family the greys already occupy. No third hue is introduced.

TokenLightDarkWhat it is for, and why it could not be an existing value
--paper #ffffff #151e22 The record. The diff, the claim cards, the source extract, section text and tables of record move off --surface onto this. Today the masthead and a claim card are the same value, so the moment the masthead turns to glass the record has nothing to be. In light it is true white, because paper is the brightest thing on the screen and the chrome is a tinted pane in front of it — that is what macOS does with a document canvas against a vibrant sidebar. In dark it is one small step above --surface, deliberately small: the existing rule colours were chosen against #121b1f and a large move would make every card border vanish.
--glass-tint #f7fafb #1a262b The material the panes are made of. Never used as a fill on its own — it exists so the three alphas below are three strengths of one material rather than three unrelated colours. Cooler than --surface in light by about four points of blue, which is what makes a pane read as frosted rather than as a slightly see-through card. In dark it is a genuine step above --surface, for the reason measured above.
--glass-solid #f6f9fa #182328 The fallback every pane gets before any filter is considered. It is --glass-tint already composited over --bg, computed rather than guessed, so a browser with no backdrop-filter lands on the colour the filter would have produced instead of on the raw tint. --ink-3 reads 4.55:1 against it in light and 4.60:1 in dark; every other ink is far above. This is the value that makes the "grey text on a grey rectangle" failure impossible rather than unlikely.
--glass-edge #ffffff #5c757e The one-pixel highlight along a pane's top edge. The cheapest signal that a surface is in front of something, and the one macOS never omits. Used at low alpha inside a shadow token, never as a fill. White in dark would read as a scratch, so dark takes a lifted grey.
--glass-cast #04191f #000000 The hue a cast shadow is made of. A blue-black rather than a neutral black in light, so a shadow belongs to the same cool family as the greys instead of muddying them. The app currently reaches for --hatch when it wants a shadow, which is an ink at 16% — right for a hairline, wrong at a 32px radius, where it goes brown.

The glass ladder: three levels, and the rule that sets them

Three, and no fourth. The rule that fixes the alphas is the opposite of the reflex:

The longer a surface lives and the more words it carries, the more opaque it is. The masthead holds two words per item and you look past it a thousand times, so it can be the most transparent thing on screen. A tour tip holds a paragraph you must read once and dismiss, so it is nearly solid. The reflex — small and fleeting means see-through — produces exactly the wrong legibility, and it is where most glass work fails.
G1 — attachedG2 — floatingG3 — transient
Wears it the masthead; the review tab rail when stuck; the admin chrome bar the Clarke dock; the bug sheet; the share panel; any modal or sheet built later tour tips; toasts; suggestion pills
Behind itthe page, scrolling a whole screen the reader wants to keep their place inanything, briefly
Alpha0.720.860.92
Filterblur(20px) saturate(180%) blur(30px) saturate(170%)blur(14px) saturate(160%)
Radius0 — it spans the viewport and has no corners --r-glass, 10px--r, 3px
Depth--edge + --shadow-1 --edge + --shadow-2--edge + --shadow-3
No filter--glass-solid, for all three. See the paragraph below.

The fallback collapses all three levels into one, and that is correct. Composited over --bg, the three alphas land within one point of each other — there is no useful difference to preserve. Without the filter there is no material difference between the levels, only a difference in depth, and depth is carried by the shadow ladder and the edge highlight, neither of which needs backdrop-filter to exist. So a browser that drops the filter loses translucency and keeps the whole hierarchy. Do not invent three fallback greys to preserve a distinction that was never in the greys.

The shape every glass rule takes. Solid first, unconditionally. Glass only inside @supports. Written the other way round — declare the alpha and hope — a browser without the filter renders the raw translucent value over whatever is behind it, which is the exact failure the brief forbids.

/* Solid for everyone, first and unconditionally. */
.masthead { background: var(--glass-solid); box-shadow: var(--edge), var(--shadow-1); }

/* Glass only where the filter exists. A browser that ignores it never sees
   the translucent value at all, so it cannot render grey on grey. */
@supports ((backdrop-filter: blur(1px)) or (-webkit-backdrop-filter: blur(1px))) {
  .masthead {
    background: var(--glass-1);
    -webkit-backdrop-filter: var(--blur-1);
    backdrop-filter: var(--blur-1);
  }
}

Type

What does not change

The three registers stay, and the rule behind them stays: --face-doc is the document speaking, --face-ui is Strata speaking, --face-data is a coordinate a machine can re-read. A reader must never mistake a quotation for the product's own words, and no glass surface gets to blur that line. All three are operating-system stacks and none of them moves. No file is fetched. --measure stays 66ch, --lh-doc stays 1.72, and every size in the scale keeps its value.

Three changes, each with the screenshot that forced it

1. A tracking value for labels in narrow tracks. --t-micro at 0.09em inside a 74px grid track renders WAITING / ON A / PERSON over three lines and breaks NEXT RE-RUN across a hyphen. Tracking is what makes an eleven-pixel uppercase label readable in a row and what makes it unreadable in a column. Add one token and one rule; invent no new size.

  --track-label-tight: 0.04em;   /* the same label, in a narrow track */

.tally__label {
  letter-spacing: var(--track-label-tight);
  line-height: 1.35;
  hyphens: none;                 /* "NEXT RE-/RUN" is not a word break */
}

.project-card__counts {
  grid-template-columns: repeat(auto-fit, minmax(5.5rem, 1fr));
}

2. A weight floor on glass. A blurred backdrop lowers apparent contrast even when measured contrast holds, because the eye reads edges and a blur softens them. So: no text on a glass surface below 600 weight, and none below --t-small. That covers nav items, the wordmark, tab labels, dock chrome and pills, and it rules out the thing that would break it — body prose on glass. Do not reach for -webkit-font-smoothing: antialiased to compensate; on a Mac it thins the strokes, which is the opposite of what is wanted.

3. Long text never sits on glass, including inside the dock. The Clarke dock is G2 glass at its head, its pills row and its ask row. The transcript between them is --paper, opaque, edge to edge. This is what Mail and Messages do — a vibrant sidebar, an opaque message list — and it is the difference between a translucent panel and an unreadable one. The same rule sends the source extract, the diff quotes and every table of record to paper.

What does not happen to type, ever. Nothing resizes on scroll. The masthead condenses by collapsing its padding from --s5 to --s2, and the wordmark and nav keep their exact size and weight through it. Type that shrinks as you scroll is the single most common tell of a templated modern site, it reflows text while a person is reading, and it buys nothing a padding change does not.

Motion

The one orchestrated moment: THE SETTLE

One sequence, on page load, three bands, 420ms end to end, and it never repeats. Nothing else in the product is choreographed.

BandWhatDelayDurationEasingFrom
1the masthead0ms260ms--ease-settle opacity 0, translateY(-6px)
2the page head — title, note, rule60ms260ms --ease-settleopacity 0, translateY(8px)
3the frame around the record — h2, hr, .tabs, section rules120ms300ms--ease-settle opacity 0 only
The record itself is in band nothing. Claims, quotes, source extracts, tables and the diff are painted at full opacity in the first frame and never animate at load. The frame assembles around a document that was already there. That is the sequence saying what the product says: the filing is not something this software produced, and it should not appear to arrive.
@keyframes settle-chrome { from { opacity: 0; transform: translateY(-6px); }
                           to   { opacity: 1; transform: none; } }
@keyframes settle-head   { from { opacity: 0; transform: translateY(8px); }
                           to   { opacity: 1; transform: none; } }
@keyframes settle-frame  { from { opacity: 0; } to { opacity: 1; } }

.masthead  { animation: settle-chrome 260ms var(--ease-settle)   0ms both; }
.page-head { animation: settle-head   260ms var(--ease-settle)  60ms both; }
.main h2,
.main hr,
.main .tabs { animation: settle-frame 300ms var(--ease-settle) 120ms both; }

Two traps in that listing. First, animation-fill-mode: both ends at transform: none, so the masthead is left with no transform and its position: sticky survives; a lingering transform on a sticky element's ancestor would kill it, so do not move this animation up onto body. Second, band 3 selects the frame, not the containers. Selecting .main .shell > * would fade a parent whose opacity composites onto every claim inside it, including a withheld one, and the signature would be gone without anyone editing a line that mentions it.

Three micro-interactions

M1 — the chip opens the source. The product's central interaction, so it is the most restrained.

  • Chip fill: background-color and color, 120ms ease. Already in the sheet. Unchanged.
  • Source panel reveal: opacity 0→1 and translateX(6px)→0, 200ms --ease-sheet. No scale, no overshoot. An overshoot on a panel showing the text of an order would be a small lie about how serious the thing is.
  • The marked span inside it: no motion at all. It is already correct when it arrives. A highlight that animates in asks to be watched rather than read.

M2 — the dock arrives. transform: translateX(100%)→0 plus opacity 0→1, 340ms --ease-sheet. No scrim: the dock sits beside the page rather than over it, and a scrim would hide the screen it exists to answer questions about. No overshoot: a 26rem rail that overshoots shows a strip of nothing at the viewport edge.

M3 — the suggestion pills. The one spring in the product. opacity 0→1, translateY(6px)→0, scale(0.96)→1, 240ms --ease-offer, which overshoots about four percent. Stagger 40ms per pill, capped at four — a fifth pill arrives with the fourth. A stagger running past roughly 200ms stops reading as one gesture and starts reading as a queue. This is the only overshoot anywhere, and it is here because a suggestion is the only thing on screen that is an offer rather than a record. Nothing rests on it, so it may be light.

Two ambient behaviours, written down so a third does not get invented:

  • A1 Project card hover: translateY(-1px) and box-shadow: none → var(--shadow-3), 160ms --ease-settle. One pixel, not four.
  • A2 Buttons, tabs, chips, nav: 120ms ease on colour only. Exactly what is there now. Do not add transform.

Arrivals animate. Departures do not.

Both the dock and the source panel are toggled with the hidden attribute, which strata.css forces to display: none !important. A transition cannot run out of display: none, but a CSS animation restarts every time an element becomes displayed — so both reveals above are animations, and neither needs a line of JavaScript changed. Closing is instant, and that is a decision rather than a limitation: a person closing a panel has already decided, and making them watch it leave is the commonest small rudeness in modern interface work.

What has no motion

  • The withheld surface and everything in it. The signature. Specified in full below.
  • Every number. No count-up, ever. These counts are findings withheld and items waiting on a person; a number that animates from zero displays a false value for 800ms, and in a compliance tool that is not a flourish, it is a wrong reading on screen.
  • Anything triggered by scroll. No reveal-on-scroll, no parallax, no fade-in-on-enter. The record is not a slideshow, and a reader scrolling back up a diff must find it exactly as they left it.
  • The diff. Before and after are paper: no blur, no shadow past a hairline, no transition, no hover.
  • The source extract and its marked span.
  • The type scale. Nothing resizes at any time.

Reduced motion removes motion. It does not shorten it.

The block at the foot of strata.css is wrong against this requirement today and must be replaced, not extended. It currently sets animation-duration: 0.01ms and transition-duration: 0.01ms, which shortens motion to the point of invisibility but leaves every animation and transition running — the events still fire, the compositor still works, and an element mid-animation at a repaint can still flash. Replace it with the block below.
@media (prefers-reduced-motion: reduce) {
  /* Removed, not shortened. A reader who asked for stillness gets the end
     state directly: no keyframes run, no property transitions, and the one
     smooth scroll in the source panel becomes a jump. */
  *,
  *::before,
  *::after {
    animation: none !important;
    transition: none !important;
    scroll-behavior: auto !important;
  }
}

With animation: none the fill mode goes too, so the three settle bands render at their natural state — full opacity, no transform — which is exactly the intended end state. Nothing needs a second declaration to undo them. tour.js already scrolls with behavior: "instant", so no script defeats this.

The signature

THE WITHHELD CLAIM IS THE ONLY SURFACE IN THE PRODUCT WITH NO EFFECTS AT ALL.
No blur. No shadow. No transform. No transition. No animation. No hover. No cursor change. When a reader reaches a claim the system refused to assert, the interface goes flat and still.

Three selectors carry it, because the refusal has three forms and they are one thing: .claim--withheld on a change page and on a shared claim, .queue__row in the escalation queue, and .withheld — the hatched slot — wherever it appears, including inside the assistant's replies and inside a blocked plan step.

Why this encodes the product rather than decorating it

The usual hierarchy gives the most important thing the most treatment. This inverts it, and the inversion is the argument. Everything else on a Strata screen responds to a person: a card lifts, a chip fills, a panel slides, a pill springs, a masthead lets the page show through it. One surface does not. It does not respond to the cursor, it does not join the page-load sequence, it does not float, and it does not cast a shadow. It is the only place the interface has nothing to offer, which is precisely what the system is telling the reader: we could not verify this, so we will not say it, and there is nothing here to make that easier to accept.

The test that keeps it the signature. The withheld surface must be the stillest thing on any screen it appears on. If a second element ever competes — equally still and equally prominent — the second element gets motion, or it is cut. Nothing is added to the withheld surface to win the comparison.

Focus, and the ring that must not be lost

The focus ring is an outline, in every scheme, on every surface, glass included. The halo is an addition and may be lost without harm.

:focus-visible {
  outline: 2px solid var(--focus);
  outline-offset: 2px;
  border-radius: var(--r-sm);
  /* The halo separates the ring from a busy or translucent backdrop. It is
     a box-shadow, so the withheld surface drops it -- which is fine, because
     that surface is opaque --surface-sunk and the ring already reads 6.1:1
     against it in light and 10.6:1 in dark. Measured, not assumed. */
  box-shadow: 0 0 0 4px var(--focus-halo);
}

Three rules for whoever builds this:

  1. Never write outline: none. Not on a glass pane, not on a card, not to "clean up" a control. The existing .tab:focus-visible { outline-offset: -2px } stays, because the tab rail scrolls and an outset ring would be clipped at the first and last section.
  2. Keep the ink-coloured ring on filled controls. .btn--primary, .citation-chip and .skip already switch outline-color to --ink, because an accent ring on an accent fill disappears. Any new filled control on glass joins that list.
  3. Check the ring on G1, G2 and G3 before shipping, in both schemes. Tab to every control in the dock, the tour tip and the masthead. No test in this repository catches a lost ring.

Two layout consequences, both measured

Sticky chrome needs an offset token, and three places must use it

Making the masthead sticky puts it over anything that scrolls beneath, including two things that are themselves positioned and one that is jumped to by anchor. All three break silently.

.masthead { position: sticky; top: 0; z-index: 30; }

/* The source panel already sticks. Without this it slides under the
   masthead and the reader loses the top of the cited section. */
.split__aside { top: calc(var(--stuck) + var(--s4)); }

/* Anchor targets. change.html gives every claim an id and links to it;
   review.html jumps between sections. Without a scroll margin the anchor
   lands behind the masthead and the reader sees the middle of the thing
   they asked for. */
.claim, .tabpanel, .queue__row { scroll-margin-top: calc(var(--stuck) + var(--s4)); }

The review tab rail sticks below the masthead at top: var(--stuck) and takes G1 glass when it does. That page is 8,823px tall with nine sections; the rail is the only thing that tells a reader where they are, and today it leaves the screen 304px in.

The change page's dead column

Measured: 416px wide, 0px tall, on the screen the whole submission rests on. Collapse the track when no panel is open.

.split:not(:has(.source-panel:not([hidden]))) {
  grid-template-columns: minmax(0, 1fr);
}

The cost, stated rather than hidden. Pressing the chip now reflows the grid in one frame. Do not transition grid-template-columns to smooth it — that animation is expensive, it janks, and it would drag the claim text sideways while someone is reading it. The panel's own 200ms fade covers the change. The alternative — floating the source panel over the claim as a G2 pane — was rejected outright: the reader is comparing a quote against its source and the two must be visible at the same time, which is the entire reason the panel is beside the claim rather than in a modal. A browser without :has() keeps today's dead column and loses nothing else; the stylesheet already relies on :has() for the deliverable tripwire.

Critique of this plan, before it is handed on

The client has rejected templated work. So: what would a generic answer to "make it look Mac-like" produce, and does any part of this arrive at the same place? Six checks, and three of them changed something.

The generic moveWhere this plan lands
Frosted cards everywhere. Rejected, and the direction was tightened. Glass sits on chrome only. The brief lists "project cards on hover" as glass and I am declining the backdrop-filter there: what sits behind a project card is flat --bg, and a blur of a flat colour is indistinguishable from a tint at roughly ten times the cost. The card gets --shadow-3 and a one-pixel lift, which is the part of the effect that was doing the work.
A purple-to-blue mesh gradient behind everything. Rejected twice over. No third hue: the five new values are white, two cool greys, a blue-black and a near-white, all inside the family the greys already occupy. And no gradient behind the page: a gradient changes the apparent colour of the paper as the reader scrolls, and for a product whose argument is exact quotation, a substrate that shifts under the text is a small continuous lie. The page floor stays flat --bg.
Spring-in-on-scroll, everywhere. Rejected. One page-load sequence, three micro-interactions, one spring, and zero scroll-triggered motion. The strongest line in the plan is the one about numbers: a count that animates from zero shows a false value for 800ms, and these counts are findings withheld.
12–16px radius on every surface. Changed after writing it. The first draft kept --r at 3px everywhere, which is right for a filing and wrong for a 26rem floating rail — it looked unfinished against the Mac reference. The resolution is a boundary rather than a global: only G2, the free-floating pane, takes --r-glass at 10px, because it is the only surface that is genuinely a window. G1 spans the viewport and has no corners. G3 and all paper keep 3px. macOS windows have a radius; macOS text fields do not.
Translucent panel, long text on top of it. Changed after looking at the dock screenshot. The first draft made the whole dock G2. The transcript is the longest prose in the product and it would have been the least readable text on screen. Now the dock's head, pills and ask row are glass and the transcript is paper — a vibrant frame around an opaque list, which is what Mail and Messages do and which turns the legibility problem into a non-problem instead of a trade-off.
Fade the whole page in on load, staggered from below. Changed, and this was the important one. The first draft made band 3 the record itself. Then the parent's opacity composites onto every child, so the withheld claim would have faded in with everything else and the signature would have been quietly gone — with no line in the diff mentioning it. Band 3 now selects the frame: headings, rules, the tab rail. The record never animates. And that turned out to say something truer than the first version: the frame assembles around a document that was already there.

One more thing the critique changed. The first draft revealed the signature at page load — the withheld claim would be the only element already at full opacity while everything else faded in. That is a two-second trick a reviewer can easily miss. The signature is now revealed by use: move a cursor across a change page and every surface answers — the card lifts, the chip fills, the panel slides — until the cursor reaches the withheld claim and nothing happens at all. That is harder to miss and it survives a reader who arrives by anchor link, by back button, or with reduced motion switched on, none of which ever see a page-load sequence.

What I am not sure about

Four things, said here rather than discovered at the panel.

  1. Dark glass may be too subtle to be worth the cost. --glass-solid at #182328 against a #0c1316 page is a real step, but a 20px blur of a dark, mostly empty page returns something close to a flat tint. If it reads as a plain panel on a real dark screen, the honest move is to drop backdrop-filter in dark entirely and keep the tint, the edge and the shadow. That would cost nothing visible and save a compositor pass. Nobody has looked at this on an actual display in dark yet.
  2. The 41% dead column may want a better answer than collapsing. Collapsing removes the waste but leaves the claim column at 58ch inside a 76rem shell, so the screen is still mostly margin. A second version might put the change's own metadata — materiality, obligations touched, the reviewer — in that column permanently, so it is never empty and the grid never reflows. That is a product decision, not a CSS one, and it is out of scope here.
  3. Reduced motion via transition: none !important is blunt. It removes colour transitions on hover as well as movement, which is more than the preference strictly asks for. It is the reading the brief requires — remove, do not shorten — and it is defensible, but a person who set the preference for vestibular reasons has also lost a 120ms colour fade that would not have troubled them.
  4. Nothing here has been opened on a handset. The 390px screenshots come from a headless Chromium at a fixed viewport. A phone has a real backdrop-filter cost, a real address bar that resizes the viewport, and a real thumb. The same caveat already stands at the foot of strata.css and it still stands.
